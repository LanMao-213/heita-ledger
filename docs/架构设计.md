### 1.2 状态管理：4 个领域 Store + `InheritedNotifier`，不引框架

原版是 `Store extends ChangeNotifier` 单例，**819 行**，同时管 tab、账本、账户、分类、模板、目标、周期游标、明细、统计、预算、借贷、筛选、补记闸、通知合并。问题不是 `ChangeNotifier` 本身（它的开销在这个数据量下可忽略），而是**一个巨型可变对象 + 全树重建**。

**方案**：

| Store | 职责 | 预估行数 | 谁 listen |
| --- | --- | --- | --- |
| `ShellStore` | `tabIndex`、当前 `AppPalette`、触感开关、`ready` 标志 | 120 | `HomeShell`（只这一处） |
| `BookStore` | 当前账本 id、期游标 `(cycleFrom, cycleTo)`、当前期明细页（keyset 分页）、当前期合计、筛选/搜索态、`listDirty` | 300 | `DetailPage` 子树 |
| `CatalogStore` | 账户、分类（含 archived）、模板、储蓄目标、净资产 | 180 | `MinePage` / `PlanPage` / 分类页 / 录入面板的分类行 |
| `PlanStore` | 预算（总额 + 分类）、借贷列表、周期账单、**统计快照**（含 `loaded/stale`） | 320 | `PlanPage` / `StatsPage` / `DebtsPage` |

跨 store 的写操作（如"记一笔"要同时动 `BookStore` 的明细与 `CatalogStore` 的账户余额）由 **`Repo` 层的一个事务 + 各 Store 的 `reload()`** 完成，不引入"store 互相持有"。

**注入**：`lib/core/scope.dart` 用 `InheritedNotifier` 写 4 个作用域（约 90 行），用法固定两档：

```dart
// 只读不重建（事件回调里）
AppScope.bookOf(context).saveTxn(...);
// 订阅重建（build 里）
final book = AppScope.watchBook(context);
```

**放弃 `provider` 包**：本机缓存里有 `provider 6.1.5+1`，它确实更省事，但我们只需要"往下传 + 订阅"两件事，`InheritedNotifier` 90 行就能覆盖；多一个包就多一处 `pub get` 解析与版本联动风险，而这个项目最大的外部风险就是依赖获取（§9-R1）。

**放弃 `Riverpod`**：① 要新增 `flutter_riverpod`/`riverpod`/`state_notifier` + 若用代码生成再加 `riverpod_generator`/`source_gen`/`build_runner`/`analyzer`，本机缓存全无；② 本项目没有异步依赖图、没有 provider 缓存失效、没有自动 dispose 需求（就是 4 份内存快照）；③ Riverpod 的 `autoDispose` 与 `ref.invalidate` 语义是**新 bug 源**——一个记账 App 里"某个页面拿到的数字被悄悄 dispose 成空"比"全树重建一次"危险得多；④ 原版 297 条测试证明 `ChangeNotifier + 纯函数 Repo` 完全可测。

**放弃 `BLoC`**：98 条功能要写 30+ event 类，样板代码量超过业务逻辑。**放弃 `GetX`**：全局单例 + 隐式依赖，测试里无法隔离两本账本。

**两条硬规则**（写进 `analysis_options.yaml` 注释 + review 清单）：
1. `notifyListeners()` **只允许**在 Store 内、且必须在 `batchNotify()` 体内或在"用户显式操作"的入口（切 tab、切主题）。页面层禁止 `setState` 后手动调 store 的通知。
2. 订阅粒度到**叶子**：`AmountText`、`TxnRow`、`ProgressBar` 不订阅任何 Store，只吃构造参数。`DetailPage` 订阅 `BookStore` 一次。

### 1.3 数据库：`sqflite` 手写 SQL，不上 `drift`

**选 `sqflite` 的理由**

1. **业务口径本身就是 SQL**。盘点 §3.2/§3.15 要求"往返归集 + 借贷排除"在 6 处聚合里完全一致，原版靠 `_expSumSql`/`_incSumSql` 两个常量收敛（`repo.dart:725-736`）。新项目把这甚至收敛成 `sql_fragments.dart` 里的 3 类常量（`expSum`/`incSum`/`excludeDebt`），**所有 repo 只能拼这些常量，不许自己写 `SUM(amount_cents)`**。ORM 的 DSL 会把这条纪律藏进生成代码里，反而更难审计。
2. **改一个字段不需要跑代码生成**。`drift` 的 `*.g.dart` 一旦忘记 regen，编译能过、运行行为是旧的——这类失败模式在 10 张表 / 100+ 查询的规模上代价高于类型安全带来的收益。
3. **迁移只有一条链、全在一个文件**。schema v1 是新起点，但**旧备份导入**要处理 v5/v6/v7/v8 四种历史形态，这是数据规范化问题（纯 Dart），不是 DDL 版本问题。`drift` 的 schema verifier 帮不上旧备份。
4. **依赖可得性**：`drift` 需要 `drift`/`drift_dev`/`analyzer`/`build_runner`/`source_gen`/`build` 一串包，本机缓存全无。

**放弃 `drift`** 的代价与补偿：

| 代价 | 补偿措施（可验证） |
| --- | --- |
| 无类型安全的列引用 | 每张表一个 `XxxColumns` 常量类（`static const id = 'id';`），repo 里不出现裸字符串字面量 |
| 手写 `toMap/fromMap` 可能漏列 | `schema_test.dart` 断言 **每个模型的 `toMap().keys` 集合 == DDL 里该表的列名集合**（从 `PRAGMA table_info` 读），漏一列就红。原版 `txn.updated_at` 死列、`Txn.toMap()` 不写它，就是这条缺失导致的 |
| 无 `watch` 流式查询 | 不需要：数据量小、写操作都走 Store 的统一 `reload()`，见 §5 |

**测试用 `sqflite_common_ffi` + Windows 系统 SQLite**（照抄原版 `pubspec.yaml` 的 `hooks.user_defines.sqlite3.windows: system`，避免从 GitHub Releases 下载 dll 超时）。Android 侧 SQLite 版本差异见 §9-R7。

### 1.4 图表：`CustomPainter` 自绘

需求只有 4 种图：环形饼（按金额降序套色阶）、分类排行横条、每日柱（可点、零值不画）、近 6 段双柱。

- `fl_chart` 本机缓存没有，且上面 4 个行为里有 3 个要覆写它的默认（色阶顺序、零值处理、点击粒度）。
- 自绘总共约 590 行（4 个 painter + 1 个公共坐标轴工具），可**像素级单测**：把 painter 画到 `ui.PictureRecorder` → `toImage` → 读像素，断言"金额最大的分类占到第 1 档色""某天零支出的柱宽为 0"。这是 fl_chart 做不到的（它的绘制细节不在我们手里）。

### 1.5 金额：`int` 分 + `Money` 值类

```dart
/// 单位恒为「分」。禁止与 double 混算，禁止直接 print。
@immutable
class Money implements Comparable<Money> {
  const Money(this.cents);
  final int cents;
  static const zero = Money(0);
  static const maxAbsCents = 999999999999; // ≈ ¥99.99 亿，与键盘上限一致

  Money operator +(Money o); Money operator -(); Money abs();
  Money operator *(int n);
  String format({bool sign = false, bool trimZero = false, bool compact = false});
  static Money? tryParseYuan(String s);   // "1,234.56" / "¥12" → 分；非法返回 null
  static Money parseYuanOrZero(String s); // 非法返回 zero（导入路径用，与 Fmt.parseCents 一致）
}
```

- 所有模型字段名以 `_cents` 结尾，`int` 类型。`schema_test` 断言：任何以 `_cents` 结尾的键的值类型必须是 `int`。
- 键盘表达式内部用 `double`，**只在最后 `(v*100).round()` 取整一次**（`calc_service.dart` 一比一移植原版 `calc.dart` 的 13 条规则）。
- Excel 是**元**、JSON 备份是**分** —— 两个方向都由 `Money.tryParseYuan` / `Money(cents)` 承担，各自有专门单测（`¥1,234.56` → `123456` 且 `-38.5` → `-3850`）。

### 1.6 日期：`LocalDate` 值类

```dart
/// 只表示「哪一天」，无时区、无时分秒。可作 Map 键、可直接比较。
@immutable
class LocalDate implements Comparable<LocalDate> {
  const LocalDate(this.year, this.month, this.day);
  static LocalDate? tryParse(String s); // 只认 YYYY-MM-DD / YYYY/MM/DD / YYYYMMDD
  static LocalDate today();
  String get iso;                       // 持久层唯一格式
  LocalDate addDays(int n);             // 用 DateTime(y,m,d+n) 走日历进位，不用 Duration
  LocalDate addMonths(int n, {bool clampToMonthEnd = true});
  static int daysInMonth(int y, int m);
  bool operator <(LocalDate o);
}
```

**为什么不用 `DateTime`**：`DateTime.parse('2026-10-16')` 得到的是本地时区午夜；`add(Duration(days: 1))` 在夏令时地区会跨错天（国内没有，但**用户改系统时区/时间**是真实场景，原版"回前台补记"就依赖日期比较）。`LocalDate` 让"日期"和"时刻"彻底分离：`created_at`/`closed_at` 用 `DateTime`（需要时分秒），业务日期一律 `LocalDate`。

**周期**：`Period` 值类（`from`/`to` 两个 `LocalDate` + `contains`/`shift(n)`/`label`），从原版 `cycle.dart` 一比一移植：账单日当天算新一期（`>=`）、短月收拢到月末、`shiftCycle` 按"期首日 ± N 月"重算而不是加 30 天、抬期 R1 只对"收入 + 白名单分类 + 早于同月账单日"生效。**这个文件是纯函数、不含 IO、行覆盖率要求 100%**。

## 2. 目录结构与完整文件清单

### 2.1 分层约定

```
lib/
  core/      值对象与跨层基础设施（无 Flutter 依赖，除 scope）
  theme/     调色板 / 字号 / 间距 / ThemeData 工厂（唯一允许出现十六进制色值的地方）
  data/
    db/        DDL、连接、迁移、种子             （不含业务口径）
    models/   每表一个模型 + toMap/fromMap       （不含 SQL）
    repo/     按领域拆的读写，每文件 ≤ 250 行     （不许跨领域写）
    services/ 纯函数口径 + 文件级服务
  stores/    4 个 ChangeNotifier
  ui/
    shell/  boot/  widgets/  pages/<feature>/
```

**四条硬约束**（review 必须逐条过）：
1. `lib/data/repo/` 下每个文件 ≤ 250 行；`repo.dart` 门面 ≤ 130 行，且**只允许转发与跨领域事务编排，不允许出现 `SELECT`**。
2. `lib/ui/` 下**禁止出现** `Color(0x`、`Colors.`、`const TextStyle(color:` —— 颜色只能来自 `context.pal.*`。门禁脚本 `tools/check_theme_hardcode.sh` 用 grep 强制。
3. 每个 `lib/ui/widgets/*.dart` 必须有 ≥1 个调用点；`tools/check_dead_public.sh` 对 `widgets/` 做"声明类名在 `lib/` 内被引用"的粗检。（原版 `PeriodChip` 零调用点活到 1.4.5 的教训）
4. **数据层每个写接口必须在 `lib/ui/` 有入口**：`test/dead_write_api_test.dart` 用"repo 里的 `Future<...> deleteXxx/createXxx/setXxx` 方法名，在 `lib/ui/` grep 至少 1 次调用"来钉住。（原版 `deleteDebt` 有此层无此门的教训）

## 3. 数据模型

### 3.1 约定

- 金额：`INTEGER`，单位**分**，列名一律 `*_cents`。允许负（净额记账），除 `debt.amount_cents`（本金必须 > 0）。
- 日期：`TEXT`，`YYYY-MM-DD`；月份 `YYYY-MM`；时刻 `TEXT` ISO8601 本地（`created_at`/`closed_at`）。
- `PRAGMA foreign_keys = ON`（`onConfigure`）。
- **硬关联**（建 FK）：`ledger_id`（全部业务表 → `ledger` `ON DELETE CASCADE`）。
- **软关联**（不建 FK，原版有意为之）：`category_id`/`account_id`/`to_account_id`/`debt_id`/`template_id`/`recurring_id`。理由：删分类要把流水变"未分类"而不是删流水；删账户要让流水保留。孤儿由 `integrity_service` 检查（§3.5）。
- **派生值不落库**：`debt.repaid_cents`、借贷 `remaining`、预算的"已用"、净资产、统计——全部现算。

### 3.4 余额恒等式（新库的硬不变量）

```
对每个 account：
  balance_cents == opening_cents + Σ(该账户流水金额影响)
  其中 收入 +amount_cents / 支出 −amount_cents / 转账转出 −amount_cents / 转入 +amount_cents
  且 amount_cents 允许为负（不做 ABS）

opening_cents 只允许被两处改写：
  ① 用户在「账户管理」里手填"当前余额" → 反算 opening = 手填 − 流水合计
  ② 用户在「数据体检」里点「重算余额」 → 只改 balance，不改 opening
  ③ 导入旧备份时认一次基准（反算），且只在真缺这一列时执行（幂等，重复反算会把漂移"吃"进基准）
```

这条恒等式在**每一次**账户相关写操作后被 `account_repo_test` 断言（§7 不变量 I1）。

## 4. 核心流程时序（编号步骤）

### ① 记一笔保存（含事务、余额更新、通知合并）

前置：`RecordSheet` 已持有面板状态（模式 `expense/income/lend/borrow`、表达式、分类、子分类、详情四字段、日期、账户、抬期开关、模板 id）。

1. `RecordKeypad` 的确认键 → `CalcService.cents(expr)`。返回 `null`（空/未输完/除零/超上限）→ 键盘确认键置灰，不进入保存。
2. `RecordSheet` 校验：借贷模式额外要求 `cents > 0 && counterparty.trim().isNotEmpty`；普通模式允许 0 与负数。
3. 算归属期：`Period.periodStartOf(date, cycleStartDay, liftToNext: liftOn)`。**这个值与第 8 步的 toast 文案共用同一个变量**，不重算（原版教训：两处各算一次 → 文案与跳转不一致）。
4. 借贷模式走 `Repo.createDebt`（一个事务三写：插 `debt` → 插本金流水（借出=expense / 借入=income，挂 `debt_id`）→ 改余额）。**借出强制 `count_in_budget = 0`**。
5. 普通模式走 `Repo.insertTxn`，事务内依次：
   5.1 `INSERT INTO txn (...)`（`period_start` 用第 3 步的值；`category/account/debt/template/recurring` 均软关联）；
   5.2 `UPDATE account SET balance_cents = balance_cents + sign(amount)`（无账户则跳过）；
   5.3 若用了模板：`touchTemplate(id)`（`use_count+1` + `last_used_at=now`）。
6. `BookStore.afterTxnInserted(periodStart)` 包在 `batchNotify` 内：
   6.1 清筛选（若在筛选态）；
   6.2 `periodStart != cycleFrom` → 搬游标（`Period` 重算 from/to）；
   6.3 `tabIndex = 0`（从图表/计划页记的也回明细）；
   6.4 重查：`accounts + netWorth`（1 查询）→ 当前期 `totals + 明细第一页 + 预算`（3 查询）；
   6.5 `planStore.markStatsStale()`（**不查统计**）；
   6.6 `planStore.reloadDebtsIfNeeded()`（仅当这笔有 `debt_id`）。
7. `batchNotify` 退出 → **只发一次** `notifyListeners()`。`DetailPage` 重建一次。
8. 面板 `Navigator.pop(RecordOutcome(periodStart, periodLabel))`；`HomeShell` 收到非 null → `Haptics.success()` + toast「已记账 · 10-01 至 10-31」。取消 → null → 不震不提示。
9. 失败（任意步骤抛）→ 事务已回滚 → toast「保存失败：{err}」→ 面板不关闭，`_saving` 复位。

**通知次数要求：正常保存 = 1 次**（`book_store_test` 断言；§7 不变量 I12）。编辑/删除同构，也是 1 次，但**不搬游标**（用户正看着那一行）。

### ② 周期账单补记（两个触发点 + 三道防重复闸）

**触发点（只有两个，都在 Store 层，UI 不直接调）**
- `boot` 序列第 8 步（冷启动）；
- `AppLifecycleListener.onResume` → `PlanStore.catchUp()`（回前台）。进 `catchUp` 前先判：「今天的 `LocalDate` 与上次见到的相同 **且** 账本未变」→ 直接返回 0，不做任何查询；再记 `wasCurrent = isCurrentPeriod`，只有 `wasCurrent` 为真才 `resetCycleToToday()`（用户正翻旧账不被拽回）。
- 切账本 `switchLedger(id)` 后也会调 `catchUp()`（这条算"触发点的一次显式调用"，不是第三个独立钩子），成功后 toast。

**三道闸**

| 闸 | 位置 | 内容 | 防的是 |
| --- | --- | --- | --- |
| 闸一：**按账本**的"今天扫过"游标 | `PlanStore._scannedOn: Map<int, LocalDate>` | 键是 `ledgerId`，不是全局时间戳。`Db.wipeAllData` / `reboot` 后必须清空 | 24h 内切到另一本账被误挡，那本账永远不补（原版用过全局时间戳，踩过） |
| 闸二：**在飞 Future 复用** | `Future<int>? _inFlight` | 同一时刻两次调用复用同一个 Future，不新开一条 | 冷启动与回前台撞车 |
| 闸三：**物理唯一** | `ux_txn_recurring_date` 部分唯一索引 + `INSERT OR IGNORE` | 插入返回 rowid 0 → 视为"已存在"，**仍然推进日期**（不 break） | 前两闸同时失效时（多进程/异常重启）的最后一道 |

**算法（`RecurringRepo.runDueRecurring`）**

1. 查 `enabled = 1 AND next_run_date <= today`，按 `next_run_date` 升序。
2. 逐条：`guard = 0`；`while runDate <= today && guard++ < 60`：
   2.1 `end_date != null && runDate > end_date` → break；
   2.2 算 `periodStart = periodStartOf(runDate, cycleStartDay, liftToNext: 白名单命中)`；
   2.3 `INSERT OR IGNORE INTO txn (... recurring_id, date=runDate, period_start)`；若插入成功 → 同事务 `applyBalanceDelta`；若被忽略 → 只记日志不抛；
   2.4 `runDate = Recurring.advanceDate(runDate, freq, interval)`（`monthly` 月末对齐：1-31 + 1 月 → 2-28/29，不溢出到 3 月）；
   2.5 计数 `added++`。
3. 写回 `next_run_date = runDate`（单事务内整条规则一起提交）。
4. 返回 `added`。`added > 0` → 调方**重查 `accounts` 与 `netWorth`**（否则"明细多了一笔房租，余额却没动"），并 toast「已补记 N 笔周期账单」。

**交易日期 = 规则本应触发的日期**（`runDate`），不是补记当天。

### ③ 从 JSON 备份恢复（含旧 schema 升级）

同一份实现服务两处：`MyPage → 从备份恢复`（选文件）与 `SafetyPage → 用它恢复`（选快照）。入口不同，流程完全一致。

1. 选文件：`file_picker` 用 `FileType.any`（Android 常把 `.json` 认成 `application/octet-stream`）+ `withData: true`。
2. `BackupService.summarize(bytes)`：解析 → 校验 `format == 'heita-ledger-backup'` / `formatVersion <= 1` / `schemaVersion <= 当前`。**任何一种不过 → 抛 `BackupFailure` 中文文案，一行都不写库**。
3. 出二次确认：写明「这份备份里有 N 笔记录 / M 账户 / K 分类 / 导出时间」，并注明「覆盖前会自动存快照」。
4. **先写快照**：`writeSnapshot(reason: 'restore')`。写不下（磁盘满/权限）→ toast「存不下快照，已取消」→ **中止**，库不动。
5. `Db.replaceAll(payload)`：**一个事务**内 ①按反序 DELETE 10 张表 ②按父表先插正序 `INSERT OR REPLACE` ③`setting` 只写 `current_ledger_id`/`cycle_start_day`/`ui.*`/`theme.palette`（机器状态先记下来再补回）。事务内失败 → 整体回滚，界面提示「恢复失败，数据未改动」。
6. 若备份 `schemaVersion < 当前` → 在**同一个事务内**调 `LegacyPatch.apply(payload.schemaVersion)`（原版 `upgradeRestoredData` 在事务外，是已知 P2，新项目并进去）：
   - `< 5`：`budget.month → period_start`
   - `< 6`：分类扁平 → 两级（`legacyNames` 改名映射 + `kDemotedCats` 降级：通讯→居家/话费网费、提成→奖金/提成）
   - `< 7`：`txn.debt_id = null`、`debt` 表按空处理
7. `backfillMissingPeriods()`：`period_start` 为空的行按新库 `cycle_start_day` + 抬期白名单现算（**只写有变化的行**）。
8. `adoptCurrentBalances()`：`opening_cents` 全为 0 或列缺失 → 按 `opening = balance − 流水合计` 认一次基准。
9. `integrity.check()`：跑 5 类只读体检，结果**随成功弹窗一起展示**（"恢复完成，体检未发现问题" / "恢复完成，发现 N 项：…（可在数据体检里处理）"）。**坏账不自动修**。
10. `Stores.reloadAll()`：`current_ledger_id` 重取（含自愈）→ 清筛选 → 四 store 全量 reload → 1 次 notify。
11. 结果弹窗写清快照路径（"后悔了可以从 我的 → 数据安全 里找回来"）。

### ④ Excel 导入（列映射与错误行处理）

1. 选文件（`withData: true` 取 bytes → 主线程不解析）。
2. `compute(parseSheet, bytes)`：**隔离区**解析 xlsx → 返回 `List<List<String?>>` 原始网格（只回字符串，避免跨 isolate 对象序列化）。
3. 主线程定位列：
   3.1 取第 1 行为表头，按名字找 12 列：`日期 / 类型 / 分类 / 子分类 / 金额 / 账户 / 备注 / 出发地 / 目的地 / 对象 / 名称 / 往来`；
   3.2 认不出（缺"日期"或"金额"）→ 退回旧 6 列序 `日期,类型,分类,金额,账户,备注`；
   3.3 仍认不出 → 中止并提示「这份表格的列名对不上」。
4. 逐行归一（第 2 行起）：
   4.1 整行空 → 跳过（不计入 skipped）；
   4.2 日期：`YYYY-MM-DD` / `YYYY/MM/DD` / `YYYYMMDD` / Excel 序列号 → `LocalDate`；失败 → `skipped.add('第 N 行：日期无效')`，跳过；
   4.3 金额：去 `¥`/`,` → `Money.tryParseYuan`；`null` 或 `<= 0` → `skipped.add('第 N 行：金额无效')`（**负数净额不能从 Excel 导入**，这是原版口径）；
   4.4 类型：含「收」或 `income` → 收入，**其余一律支出**（不认转账）；
   4.5 分类：`(一级, 子分类)` 二元组 → 命中则用 id；未命中则**自动创建**（给了父名挂到父级；只给子名就单独建一级；两者都空 → `category_id = null` 即"未分类"）；
   4.6 账户：按名找，找不到自动建（`kind = other`，`sort_order = 999`）；账户名为空 → null；
   4.7 `往来` 列**只读不导入**（不建 debt）；
   4.8 算 `period_start`（同 §4-① 第 3 步）。
5. 分批写入：每 200 行一个事务（5000 行 = 25 个事务，比单事务快且不会长事务锁库）；每批之间 `await Future.delayed(Duration.zero)` 让 UI 有机会刷新进度。
6. 完成弹窗：「导入完成 · 成功 N 笔 / 跳过 M 行」+ 最多列 6 条问题行 + 「其余 M-6 条已忽略」。
7. `Stores.reloadAll()`。

### ⑤ 切账本

1. `LedgerSheet` 点非当前账本 → `BookStore.switchLedger(id)`。
2. `setting['current_ledger_id'] = id`（单写，立即提交）。
3. `_resetFilter()`（筛选里引用的分类/账户可能属于另一本账，整体清掉）。
4. `catalogStore.loadCatalog(ledgerId)` → 账户/分类树/模板/目标（这本账的）。
5. `BookStore.resetCycleToToday()` → 重算 `cycleFrom/cycleTo`。
6. `bookStore.reloadCycle()` → 合计 + 明细第一页 + 预算。
7. `planStore.reload(ledgerId)` → 预算/借贷/周期账单；`markStatsStale()`。
8. `planStore.catchUp()`（闸一按新 `ledgerId` 判，闸三兜底）。`added > 0` → toast。
9. `batchNotify` 退出 → 1 次 notify。

### ⑥ 配色切换

1. `MyPage → 偏好 → 配色` → 两个选项（柏油黑塔 / 露露缇雅·泽金）。
2. `ShellStore.setPalette(p)`：内存立即改 → `setting['theme.palette'] = p.id` 落库 → 1 次 notify。
3. `HeitaApp` 用 `ListenableBuilder(listenable: shellStore)` 包 `MaterialApp`，`theme: buildTheme(shellStore.palette, Brightness.light)`。
4. `MaterialApp` 内部 `AnimatedTheme` 自动做 **200ms** 颜色插值（`AppPalette.lerp` 逐字段插值）——不需要自己写转场。
5. 所有 UI 通过 `context.pal.xxx` 取色，**没有一处 `static const` 颜色**，所以整棵树自动跟着变。
6. 启动时 `boot` 第 5 步读 `setting['theme.palette']`，缺省 `ink`。

### ⑦ 启动序列（`BootGate`，严格顺序，任一步失败即落 `boot_error`）

`Store.ready` 为真时**直接跳过整段**（防热重载重复跑）。

1. `Db.open()`（`onConfigure` 开 `PRAGMA foreign_keys`）——失败则整页失败。
2. 库版本比包新 → `DbDowngradeException` → 文案「这份账本来自更新的版本…账目都还在，不要卸载重装」。
3. `backfillMissingPeriods()`（只补 `period_start IS NULL` 的行，正常情况下第 1 次之后恒为 0 次写）。
4. `ShellStore.loadFlags()`：`ui.haptics`（缺省开）、`ui.notice.cats`（一次性提示标记）。
5. `shellStore.setPalette(setting['theme.palette'] ?? 'ink')`（**在首帧之前定好**，避免白屏后变色）。
6. `Repo.currentLedgerId()`（含自愈：指针指错→回第一本；一本都没有→重建一本）。
7. `cycleStartDay()`（缺省 1）→ `BookStore.resetCycleToToday()`。
8. `planStore.catchUp()`（闸一按 `ledgerId` 判）→ 得到 `recurringAdded`。
9. 分类升级提示判定（新库首次安装为 `false`，不提示）。
10. `catalogStore.loadCatalog()` + `bookStore.reloadCycle()` + `planStore.reload()` → `markStatsStale()`（**统计不在启动路径算**）。
11. `ready = true` + 1 次 notify；若 `recurringAdded > 0` 或分类刚升级 → 首帧后把两者用「；」拼成**一条** toast。
12. 全程包在一个 `batchNotify` 里 → 启动只重建 1 次。

**性能**：第 1–10 步（真正的 IO 部分）总预算 ≤ 900ms（§8）。第 3 步是唯一可能有大写入的步骤，且只在旧库首次升级时发生。

## 5. 状态与刷新策略

### 5.1 一次操作的通知次数（预算表）

| 操作 | 通知次数（上界） | 查询次数（目标） |
| --- | --- | --- |
| 记一笔 / 改一笔 / 删一笔 | **1** | ≤ 6 |
| 切 tab | 1（只 `ShellStore`） | 0 |
| 切配色 / 切触感 | 1（只 `ShellStore`） | 0 |
| 翻期（明细） | 1 | ≤ 4（合计 + 明细页 + 预算） |
| 切账本 | 1 | ≤ 10 |
| 打开图表页（统计脏） | 1（异步完成后） | ≤ 5 |
| 记还款 / 标记结清 / 删往来 | 1 | ≤ 6 |
| 周期补记 N 笔 | 1 | ≤ 6（不随 N 增长） |

实现手段：`StoreBase.batchNotify(body)`（深度计数 + pending 标志，退出时只发一次），移植原版 1.4.5 已验证的写法。**它是"合并"不是"节流"**，不延后到下一帧，手感不变。

### 5.2 派生数据：即时算 vs 脏标记

| 数据 | 策略 | 理由 |
| --- | --- | --- |
| 账户余额、净资产 | **即时**（写操作同事务内维护，reload 时 1 查询） | 用户随时会看，且必须与流水分毫不差 |
| 当前期合计（支出/收入/笔数） | **即时**（reload 时查） | 概览卡就在首屏 |
| 预算（总额/已用/剩余/每天可花） | **即时**（纯函数在内存算，已用量取当前期合计） | 与合计同源，不能两套数字 |
| 借贷已还/剩余 | **即时**（`repaidIndex` 1 查询） | 剩余金额是这套功能的核心数字 |
| **统计页（饼/排行/日柱/趋势）** | **脏标记 + 上次快照（stale-while-revalidate）** | 每次记账跑 5 个聚合查询太贵，且大部分记账不会立刻看图表 |

### 5.3 统计页的正确做法（原版教训写进来）

原版两条路都试过：
- **每次记账就 `loadStats()`**（6~8 个查询，不管有没有打开图表页）→ 记账变慢；
- **完全惰性，切到图表页才算** → 图表页先画一次空态（`statExpenseStats` 初值是空 list，UI 判 `isEmpty` 就画"本期还没有数据"）。CH 1.4.5 因此撤回了这个改动。
- 而且**这个回归没被测出来**：原版 `ui_shot_test` 只断言"无溢出"，空态也能通过。

**新项目方案**：

```dart
@immutable
class StatSnapshot {
  final bool loaded;        // 是否至少成功算过一次
  final bool stale;         // 数据变了但还没重算
  final RangeCategoryStats categories;
  final List<DailyTotal> daily;
  final List<PeriodTrend> trend;
  final int accountAssetsCents;
}
```

- `PlanStore.stats` 默认 `loaded = false`。
- `StatsPage.build` 三态：
  1. `!loaded` → **骨架**（灰色圆环轮廓 + 3 条占位条），**绝不渲染空态文案**；
  2. `loaded && stale` → 先渲染旧值（不闪），同时在 `initState/postFrame` 触发 `refreshStats()`；
  3. `loaded && !stale` → 直接渲染。
- `refreshStats()` 完成后 1 次 notify；失败 → `stale` 保持 true + toast「统计刷新失败，显示的是上次结果」，**不清空旧值**。

**可验证的测试**（这条是"截图测试不自欺"的具体落地之一）：

```
test/stats_page_test.dart
  1. 造 3 笔支出，打开图表页，等 settle → 断言饼图有 3 个扇区。
  2. 回到明细，记第 4 笔，立刻切到图表页，pump(Duration.zero) 一帧：
     断言 find.text('本期还没有数据') == findsNothing，
        find.byType(PieSkeleton)    == findsNothing，
        find.byType(PieChart)       == findsOneWidget。   ← 挡住"先闪空态"
  3. 再 pumpAndSettle → 断言扇区变 4 个（新值生效）。
```

### 7.3 截图测试怎么才不自欺

原版 `ui_shot_test` 只断言"没有溢出异常"。`expect(tester.takeException(), isNull)` 只证明**没有抛异常**，空态、错位、颜色全错都能通过。新项目三档，各管一件事：

**档一：`CustomPainter` 像素断言（最有力，无字体依赖）**

```dart
// 把 painter 直接画进图片，不经过 widget 树，所以没有字体/主题/平台差异
final rec = ui.PictureRecorder();
painter.paint(ui.Canvas(rec), const Size(200, 200));
final img = await rec.endRecording().toImage(200, 200);
final bytes = (await img.toByteData(format: ui.ImageByteFormat.rawRgba))!;
// 断言：12 点钟方向顺时针第 1 扇区起始处的像素 == palette.chart[0]
// 断言：零值日期那一列在柱高范围内全部是背景色（即"零值不画柱"）
// 断言：饼图扇区角度之和 == 2π（容差 1e-6）
```

覆盖：饼图灰阶顺序、零值不画柱、双柱共用基线、排行相对长度、进度条 `clamp`。**这是唯一能真挡住"数字对但画面错"的手法**，且完全稳定（无字体、无平台渲染差异）。

**档二：布局 golden（有代价，控范围）**

- 需要中文字体：测试里 `TextStyle(fontFamily: 'TestCJK')` 指向打进 `test/fonts/` 的 Noto Sans SC **子集**（只含用到的字，约 180KB），在 `flutter_test_config.dart` 里统一加载。
- 固定 `tester.view.physicalSize = Size(1080, 2340)`、`devicePixelRatio = 3`、`textScaler = 1.0`。
- **只覆盖 6 张**：明细页（有数据/空态）、记一笔面板、计划页、往来页、我的页、图表页。两套配色各 1 张 → 共 12 张。
- 打 `@Tags(['golden'])`；**CI 只跑 `flutter test --exclude-tags golden`**，golden 只在本机手动跑（Windows 与 Linux 的 AA/字形抗锯齿有差异，跨机基线必然抖）。
- 改 UI 流程：`flutter test --update-goldens --tags golden` → **人工看 diff 图**再提交。代价写清楚：每次 UI 改动要重新审 12 张图，这是"视觉回归"的唯一诚实做法。

**档三：几何断言（替代"无溢出"的自欺）**

不用 golden 也能挡住排版错误：

```dart
// ① 金额永不超过卡片宽度（六位数 + 千分位 + 符号）
final cardRect = tester.getRect(find.byType(SummaryCard));
final amtRect  = tester.getRect(find.byType(AmountText).first);
expect(amtRect.width, lessThanOrEqualTo(cardRect.width - 32));

// ② 极端字号不溢出（原版 textScale 从未测过）
tester.platformDispatcher.textScaleFactorTestValue = 2.0;
await tester.pumpAndSettle();
expect(tester.takeException(), isNull);
expect(tester.getRect(find.byType(TxnRow).first).height, greaterThanOrEqualTo(60));

// ③ 日卡日期头三个 Text 并排不顶出屏（原版真机踩过）
final dateRect = tester.getRect(find.byKey(const Key('day-header-date-0')));
expect(dateRect.right, lessThanOrEqualTo(tester.view.physicalSize.width / tester.view.devicePixelRatio));
```

**明确说明**：这三档加起来覆盖"画对了""排对了""在极端条件下还对"，但**不覆盖"好不好看"**。后者只能靠真机走查清单（`docs/发布检查清单.md`，阶段 6 产出）。

### 7.4 测试纪律

- 数据层测试一律用 `sqflite_common_ffi` 的**内存库**（`inMemoryDatabasePath`），每个 test 前建、后关，互不污染（原版共用文件名在 Windows 上删不掉文件）。

## 8. 性能预算

目标设备基准：中端机（骁龙 6 系 / 天玑 700 级），数据集 **5,000 笔流水 / 20 账户 / 100 分类 / 5 本账本**。

| 场景 | 预算 | 说明 |
| --- | --- | --- |
| 冷启动 → 首帧可见（开屏） | ≤ 400ms | 首帧只画开屏，不做任何 DB 查询 |
| 冷启动 → 明细页可交互 | ≤ 900ms | boot 序列：open(50) + backfill(仅首次有量,≤200) + uiFlags(5) + ledger 自愈(5) + cycle(1) + catchUp(≤150) + loadAll(≤350) |
| 翻期（明细） | ≤ 120ms | 4 个查询：合计 + 明细首页 + 预算 + 分类预算 |
| 记一笔保存 → toast 出现 | ≤ 150ms | 事务 + 6 查询 + 1 次重建 |
| 明细滚动 | 60fps，掉帧率 < 2% | `SliverList.builder` + 行内无 `Opacity`/`ClipRRect` 叠加 |
| 当前期合计（5,000 笔里一期约 300 笔） | ≤ 15ms | 走 `idx_txn_ledger_period` |
| 分类统计（一期约 40 个分类） | ≤ 25ms | 1 个 `GROUP BY COALESCE(parent_id,id)` |
| 近 6 期趋势 | ≤ 40ms | **合并成 1 条查询**（`GROUP BY period_start` + 区间 IN），不是原版的逐段 6 次 |
| 统计页整页（5 查询） | ≤ 120ms | 只在 `stale` 时算 |
| 打开「本期全部」等价能力（滚到底 5,000 笔） | 每页加载 ≤ 30ms | keyset 分页，每页 50 条 |
| 内存在 Store 的流水 | ≤ 300 条（当前页 + 缓冲），不缓存全量 | 原版 `txns` 一次 500 条就在内存里 |
| Excel 导入 5,000 行 | ≤ 3s（隔离区解析 ≤ 1.5s + 25 个事务写入 ≤ 1.5s） | 主线程不解析 |
| 备份 dump 全库 | ≤ 2s | 10 次全表 `SELECT` + `jsonEncode`（可在隔离区编码） |
| APK 体积（arm64 release，split） | ≤ 22MB | 无图标资产、无字体资产、无多余插件 |

### 8.1 分页：keyset，不用 offset

```sql
-- 第一页
SELECT * FROM txn
WHERE ledger_id = ?1
ORDER BY date DESC, id DESC
LIMIT ?2;
-- 后续页（游标 = 上一页最后一行的 (date, id)）
SELECT * FROM txn
WHERE ledger_id = ?1
  AND (date < ?3 OR (date = ?3 AND id < ?4))
ORDER BY date DESC, id DESC
LIMIT ?2;
```

**为什么不用 offset**：① 用户滚到第 10 页时又记了一笔（`date` 是今天，排在最前），`OFFSET 500` 会整体错位 → 同一条记录重复出现或被跳过；② offset 深翻页要扫前 N 行，5,000 条时第 80 页明显变慢；③ keyset 的 `WHERE` 正好吃 `idx_txn_ledger_date(ledger_id, date, id)`，代价恒定。

**筛选态同理**：`search` 的 500 条上限保留（原版口径），但列表分页也用 keyset；**合计另走独立聚合、不受上限影响**（原版 D20 的口径，必须保持）。

### 8.2 索引使用校验

每条高频 SQL 在开发期跑一次 `EXPLAIN QUERY PLAN`，断言不出现 `SCAN TABLE txn`（`txn_repo_test` 里作为断言，防止后续改动把索引写废）。

- 问：备份 JSON 要不要**口令加密**？旧版是明文（已知 P2：分享出去等于交出整本账，含"借给谁多少"）。
  - A：V1 明文 + 导出弹窗明写"未加密，请自行保管"（原版行为，0 成本）
  - B：AES + 用户口令（`encrypt` 包，不在缓存，需新增依赖 + "忘密码=打不开"的支持成本）
- **建议 A**（V1），B 放 V2。

### Q5 · 旧数据从哪来（**这条会影响验收，最需要确认**）

- 需要用户提供（或确认是否存在）**旧版导出的 JSON 备份文件**，以及它来自哪个版本（`schemaVersion` 5 / 7 / 8）。
- 有真实文件 → 导入器可以用它做端到端验收（"笔数/月度合计/账户余额/借贷剩余/最近 3 个模板"逐项对齐），这是唯一能证明"旧账整本搬过来了"的办法。
- 没有真实文件 → 我只能用自己构造的四份 fixture（v5/v7/v7+debt/v8）测，**真实数据里的脏行（空分类、非法日期、超长备注）测不到**，上线后可能出问题。
- 一并确认：旧机上那份数据是否**只能先导出 Excel**（若那台机器装不上/打不开旧版，预算/目标/模板/周期/往来/账户余额会全丢，只剩流水 —— 盘点 §5-d-1 的那台华为 1.1.4）。
