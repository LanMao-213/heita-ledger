# 决策记录：加密备份的算法、参数与口径

> 适用于 1.6.0+26（`release/1.6.0`）。实现见 `lib/data/backup/`。
> 这份文档记的是「为什么是这些数」，不是「怎么用」—— 用法看 README。

---

## 1. 一句话结论

导出的备份可以用一个口令加密：**AES-256-GCM + PBKDF2-HMAC-SHA256（210000 次）**，
容器是 `.heita`（JSON 信封 + base64 密文）。**口令不保存，忘了就打不开；明文导出
始终保留。**

---

## 2. 算法与参数

| 项 | 取值 | 为什么 |
|---|---|---|
| 对称加密 | **AES-256-GCM** | 带认证：解出来要么完整、要么失败。这个功能最怕的是「解出乱码」被当成合法数据灌进库 |
| 密钥派生 | **PBKDF2-HMAC-SHA256** | 每个平台都自带实现、不需要额外原生库；参数只有一个（迭代数），好解释 |
| salt | **16B**，`Random.secure()` | 每次导出都不同，同一口令在不同文件里派生出不同密钥 |
| nonce | **12B**，`Random.secure()` | GCM 的 nonce 一旦重复，同密钥下明文会泄漏 —— 必须用密码学随机源 |
| tag | **16B** | 截断末 16 字节能被立刻发现，靠的就是它 |
| AAD | `format\|containerVersion\|kdf\|iter\|salt\|cipher\|nonce` 的确定性串 | 把头部每个字段钉死：改 salt / nonce / iter / containerVersion 中任何一个，认证都失败 |
| 迭代数 | **210000** | 见下一节的实测 |

### 实测（`flutter_tester`，纯 Dart 实现，Windows 本机）

| 迭代数 | 一次派生 | 20k 笔（3.04MB）seal | 20k 笔 unseal |
|---|---|---|---|
| **600000**（设计意图） | **3727 ms** | 4754 ms | 4688 ms |
| **210000**（最终选定） | **1242–1297 ms** | 1845 ms | 1772 ms |

拆开看，一次 seal ≈ KDF + GCM：

- KDF：210000 次约 1.25s（600000 次约 3.7s）
- GCM：3MB 明文约 0.5s（纯 Dart 实现，约 6MB/s）

**降级理由**：设计时打算用 600000（OWASP 对 PBKDF2-SHA256 的推荐量级），但本机
实测**单次派生就要 3.7 秒** —— 导出要等近 4 秒、恢复再等近 4 秒，用户会以为
点没反应（而这个应用是「记账时手边开着」的工具，不是年更的归档工具）。按事先
定好的规则（本机 > 2s 就降到 210000）取 210000，实测 1.24s。

**这个数的意义要说清**：210000 次对「拿到文件的人」意味着每猜一个口令要花
~1.2s（手机端更慢），配合 6 位下限的口令，离线暴力破解的边际成本是真实的。
但它**不是**「口令短一点也没关系」的许可 —— 见第 5 节。

> 若将来换到原生实现（见第 3 节），先把这张表重测一遍再决定要不要抬回 600000。

### 两个被否决的替代方案（记下来，免得再讨论一遍）

**降到 100000 迭代来换「合计 < 3s」** —— 否决。迭代数是唯一抵抗离线暴力的成本
参数：210000 已经是从 600000 降下来的折中，再降等于用安全性换 0.6 秒，而那
0.6 秒用户根本感知不到（感知到的是「有没有在跑」，见下面的进度弹窗）。

**引 `cryptography_flutter` 原生加速** —— 否决。它多一个平台插件 + MethodChannel，
会直接毁掉「加解密能在 `flutter test` 里跑」这条 —— 那个 5 路篡改测试
（改密文 1 bit / salt / nonce / iter / containerVersion）全靠它。为了 1 秒
换掉整个测试能力，不划算。将来真要做，先补一份「纯 Dart 与原生实现结果一致」
的对拍测试再说。

### 低端机的真实预期：3~5 秒

上表是 `flutter_tester`（桌面 CPU）的数字。真机——尤其低端 Android——上一次
seal/unseal 可能是 **3~5 秒**。**这就是 UI 必须给阻塞式进度的原因**（见
`lib/widgets/busy_dialog.dart`）：

- 一个 1.8 秒的**冻结**界面，体感上比 3 秒的**转圈**糟糕得多 —— 用户会再点一次
  （于是同一份备份被加密两遍）、以为崩了把 App 划掉（此时事务正在写库）；
- 所以「放宽到单次 2.5s」和「让等待可见」是一套东西，不能只放宽门限不给出反馈；
- 进度弹窗**不许点掉**（`barrierDismissible: false` + `PopScope(canPop: false)`）：
  点掉之后任务还在跑，用户以为取消了，实际只是失去了「它在跑」这个信息 ——
  比没有弹窗更迷。
- 三处都接了：加密导出、解密（仅 `.heita`）、整库恢复。

## 3. 依赖选型：为什么是 `cryptography`

| 方案 | 否决理由 |
|---|---|
| **pointycastle** | 功能全，但把密码学当**工具包**：`BlockCipher` / `PaddedBlockCipher` / AEAD 三套 API 并存。用错模式不会报错，只会安静地少一层认证 —— 而这个功能最不能接受的就是「安静地少一层」 |
| **MethodChannel 调系统 Keystore / CryptoKit** | ① 需要原生代码，每个平台各写一遍；② **导出文件是要跨设备恢复的**，平台密钥帮不上忙（换手机就解不开）；③ 多一层平台通道，过审时要额外解释。收益全在「本机存储」，而本机没有敏感数据（不联网、无账号），我们要保的是「带走的那份文件」 |
| **dart:ffi + OpenSSL** | 多一个原生二进制、多一份 ABI 兼容风险、多一个「这个 .so 是什么」的问题。能换来的只是几百毫秒的 KDF 与 GCM 吞吐，不值得 |
| **自己拼 CBC + HMAC** | 两套密钥的派生顺序、先加密还是先 MAC，每个细节写错都「看起来能用」。GCM 把这件事收进一个原语 |
| **`cryptography_flutter`**（原生加速） | 目前**没有**引入。它能显著加快 GCM 与 KDF，但代价是多一个平台插件 + 一层 MethodChannel。如果将来 20k 笔的导出耗时成为真机痛点，这是第一个该试的方案（届时把第 2 节的表重测） |

`cryptography: ^2.7.0` 实际解析到 **2.9.0**，只多一个传递依赖（`crypto`，本来就有），
**没有**引入任何原生插件、没有平台代码、没有网络能力。

## 4. 三个版本号，各管各的

| 版本 | 含义 | 当前值 | 什么时候动 |
|---|---|---|---|
| `schemaVersion` | **数据库结构** | 10 | 加表 / 加列 / 改列语义（要走迁移） |
| `formatVersion` | **payload 结构** | 1 | payload 里加字段 / 改字段名 |
| `containerVersion` | **容器封装** | 明文 1 / 加密 1 | 信封结构变化（比如换 KDF 参数编码方式） |

### `containerVersion` 与 `formatVersion` 的区别（最容易搞混的一处）

- `formatVersion` 回答「**这份数据**是哪个结构」。它跟着 `tables` 里的字段走。
- `containerVersion` 回答「**这个文件**是怎么装的」。它跟着信封（salt/nonce/iter/密文）
  的字段走。

同一个 payload（`formatVersion = 1`）既可以明文写在 `.json` 里，也可以封进 `.heita`。
**禁止用 `formatVersion` 表达「是否加密」**：那等于承认「加密过的那份数据本身不一样」，
而那是假的 —— 解出来还是同一张表，`restore` 走的还是同一条路。

### 判型只看内容，不看扩展名

恢复入口只认顶层两个字段：

- `format != heita-ledger-backup` → 不是本应用的文件，拒绝；
- `container == "sealed"` → 加密，要口令；
- 其余（含**没有** `container` 字段的老文件）→ 明文。

扩展名是给人看的：加密导出用 `.heita`，明文仍用 `.json`。用户在文件管理器里把它
改成 `.txt`、或者用聊天软件存成 `.bin`，恢复入口都必须能认出来。反过来，
`.heita` 里装着明文也照样按明文读（内容说了算）。

## 5. 产品口径：忘口令不可恢复

**我们不保存口令。它只用来加密这一次导出的文件，不写进 App 的任何地方。**

这不是偷懒，是功能成立的前提：

- 口令如果存在设备上，「加密导出」就退化成「换了个格式的明文」—— 文件离开手机
  之后，任何拿到手机的人（或任何能读那个存储的进程）都能解；
- 而这份文件的全部意义就是「离开这台设备之后仍然只有我能读」。

所以：

1. 输口令的界面**必须**写明「我们不保存、忘了打不开」——写进文案，不是写进文档；
2. 界面上**不许**出现「找回口令」「重置口令」这类词，那会让人去找一个不存在的按钮；
3. **明文导出始终保留**，与加密导出**并列同等地位**。不给逃生路径的加密，会让
   「想把数据带走」这件事在忘记口令那天彻底断掉；
4. **不做**「加密导出的同时再给一份明文」—— 一份明文躺在同一个目录里，加密那份
   就变成了摆设。

### 认证失败为什么不叫「口令错误」

「口令错了」和「文件被改了一个 bit」在密码学上**不可区分** —— 两者都只是 GCM 的
tag 对不上。所以错误类型是 `BackupSealedException(wrongPasswordOrCorrupt)`，界面
文案必须同时给出这两种可能（「口令不对，或者文件不完整」）。

把它写成「口令错误」的后果是可预期的坏：一个文件损坏的用户会反复重输那个其实
正确的口令，最后以为自己的口令丢了。

三种 `kind` 与对应文案：

| kind | 触发 | 文案要点 |
|---|---|---|
| `wrongPasswordOrCorrupt` | GCM 认证失败 / 密文过短 | 口令不对**或**文件不完整，允许重试 |
| `unsupportedContainer` | `containerVersion` 更高 / 算法标签不认识 / 迭代数大得离谱 | 「来自更新的版本，请先升级」——不猜、不降级 |
| `malformedHeader` | 缺字段 / base64 解不开 / salt 长度不对 / 空口令 | 「文件不对」，不给重试 |

## 6. 快照与导出的分工（为什么快照不加密）

| | 自动快照 | 明文导出 | 加密导出 |
|---|---|---|---|
| 谁触发 | 清空 / 恢复 / 手动「现在备份」 | 用户点「明文备份」 | 用户点「加密备份」 |
| 存在哪 | 应用私有目录（`文档/backup`） | 临时目录 → 系统分享 | 临时目录 → 系统分享 |
| 格式 | `.json` 明文 | `.json` 明文 | `.heita` 加密 |
| 会被复制几份 | 保留 3 份 / 7 天 | 用户决定 | 用户决定 |

快照**永远是明文**，因为它是兜底：它在「刚清空、现在后悔」那一刻被用到，而那时
用户手上唯一确定的东西就是这台手机。要口令的兜底在惊慌时刻等于没有兜底，更糟的
是它让人**以为**有。

这条口径靠 **import 图**保证，不靠自觉：`lib/data/backup/snapshot.dart` 不 import
`sealed_file.dart`，`writeSnapshot` 的签名里也没有口令参数。`test/architecture_test.dart`
有两条源码探针钉着它（`password` 大小写不敏感、`sealed_file` 引用），改这条口径会先
被测试拦下。

## 7. 已知取舍与后续

- **纯 Dart 的 GCM 只有约 6MB/s**。20k 笔的库（3MB）单次操作 ~1.8s，可以接受；
  但如果有人有 10 万笔（15MB），导出会到 ~5s。届时第一选择是 `cryptography_flutter`
  （原生 AES），第二选择是先在 payload 层压缩再加密。
- **没有「更换口令」**。口令只作用于单次导出的文件，要换就重新导出一次 —— 这是
  「不保存口令」的直接推论，不是缺口。
- **口令强度只做长度下限（6 位）**，不做复杂度规则。复杂度规则的实际效果是把人逼去
  写 `Password1`，然后写进备忘录。真正的防护来自 210000 次迭代造成的破解成本。
