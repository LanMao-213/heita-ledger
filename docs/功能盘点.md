**记账主闭环（记一笔 → 按日明细 → 本期预算 → 分类统计 → 周期补记）在 main 上已经闭合且数字自洽**；1.4.5 补的是「数字可校验」（余额=期初+流水、数据体检）、「补记不漏」（回前台也补）与列表懒加载。**真机验证只做到 1.4.0 完整一轮 + 1.4.1 分类页 + 1.4.5 dev 包 11 项**；1.4.2~1.4.4 的 6 项关键行为与 1.4.1 遗留的 5 项**从未在真机上点过**（CH 1.4.4「待验证」、交接 §11「没验过」）。

## 3. 业务口径专章（重做时最容易做错的地方）

> 这一节每一条都是「写错了不会崩、但数字会错」的地方。每条给出代码依据（`文件:行号`）与文档出处，并在最后一句写清**重建陷阱**。

### 3.1 预算怎么算

| 项 | 口径 | 代码依据 |
| --- | --- | --- |
| 存储 | 按**归属期**存：`budget(ledger_id, period_start, category_id, amount_cents)`，`category_id IS NULL` 那行是总预算；`UNIQUE(ledger_id, period_start, category_id)` | `db.dart:212-220`、`repo.dart:1253-1276` |
| 总预算额度 | `totalBudgetCents` = 该期 `category_id IS NULL` 的 `amount_cents`；没有记录 → `null`（不是 0） | `repo.dart:1240-1251` |
| **可用额度** | `budgetAvailableCents = totalBudgetCents + borrowedInBudgetCents`（见 3.2） | `store.dart:229-234` |
| 已用 | `expenseCents` = 本期 `rangeTotals` 的支出侧，**交叉归集 + 排除借贷**（见 3.15） | `store.dart:397-400`、`repo.dart:1087-1106` |
| 剩余 | `budgetLeftCents = totalBudgetCents == null ? 0 : 可用额度 − 已用`（**没设预算时返回 0**，不是负数） | `store.dart:236-237` |
| 超支 | `overBudget = 总额非空 && 已用 > 可用额度`；`overBudgetCents = 已用 − 可用额度` | `store.dart:239-243` |
| 进度 | `usedRatio = (cap<=0) ? 0 : 已用/cap`，不截断（超支时 >1），界面自己 `clamp(0,1)` | `pacing.dart:110-112`、`summary_card.dart:196-206` |
| 每天可花 | `left <= 0 → 0`；`remainDays==0 → 按 1 天算`；`left ~/ days`（**向下取整**） | `pacing.dart:123-128` |
| 计划日均 | `totalDays` 现算（28–31 天），`total ~/ totalDays`（**整除不是四舍五入**：每天多算 1 分，月底必超） | `pacing.dart:114-118` |
| 分类预算 | 只设在**一级**分类；「已花」要含该一级下所有子分类（`COALESCE(tc.parent_id, tc.id) = c.id`）；列表 = 设了预算的 ∪ 本期有支出的一级分类；已停用分类不出现 | `repo.dart:1323-1361` |
| 结转 | **没有 rollover**：上月剩余不带入下月（已知 P3） | 交接 §11「已知未修」 |
| 改账单日 | 预算的 key 是期首日，账单日一变必须 `remapBudgetPeriods`：按旧期首日算它落进哪一期；两条挤进同一期时**金额相加**（不是覆盖） | `repo.dart:1286-1315` |

文档出处：交接 §10「借入与预算的关系」、交接 §11（P3 预算不结转）、周期 §2（D13 预算也按周期）。
**重建陷阱**：①把「总额度」当「可用额度」去算剩余/百分比 → 借入打开后进度条与剩余对不上；②已用取「按 `date` 的当月支出」而不是「按 `period_start` 的本期支出」→ 账单日 ≠ 1 时全错；③分类预算只算 `category_id = c.id`，不含子分类 → 记到「正餐」后餐饮进度条永不动。

### 3.8 金额精度与舍入

| 规则 | 内容 | 依据 |
| --- | --- | --- |
| 存储 | 全程 **INTEGER 分**（`1000 = ¥10.00`），杜绝浮点累积误差 | `models.dart:15-20`、`db.dart:12` |
| 计算 | 键盘表达式内部用 `double`，**只在最后 `(v*100).round()` 取整一次**；每步取整会让 `0.1+0.2` 累积成分位误差 | `calc.dart:78-142` |
| 上限 | `abs(cents) > 999999999999`（≈ ¥99.99 亿）→ 视为非法，不能保存；整数位最多 9 位、小数最多 2 位 | `calc.dart:140`、`calc.dart:15-16` |
| 元→分（非键盘路径） | `Fmt.parseCents`：去逗号 → `double.tryParse` → `(d*100).round()`；空/非法返回 **0**（不抛异常） | `models.dart:104-110` |
| 负数 | 允许：净额记账（支出 −20 = 方向反了）。`-` 有两个身份：行首/运算符后是一元负号，数字后是减号，**所以没有 ± 键** | `calc.dart:7-9` |
| 显示 | `Fmt.money(123456)` → `1,234.56`（千分位）；`sign:true` 时正数加 `+`；`trimZero:true` 时整数不带 `.00`；`compact` ≥1 万元显示「1.2万」 | `models.dart:23-57` |
| 交叉归集的绝对值 | 支出里的负数**取绝对值计入收入**（不是负负得正） | `repo.dart:725-736` |

**重建陷阱**：用 `double` 存金额（真金白银的差错）；在每一步运算后取整（`0.1+0.2` 类输入会漂）；把 `parseCents` 的 0 当成「用户输入了 0」（它同时表示「非法」）。

### 3.9 搜索：一位数不当金额 + 通配符转义

| 规则 | 内容 | 依据 |
| --- | --- | --- |
| 搜哪些列 | 5 个文本列 `note/person/subject/place_from/place_to` **OR** 分类名（含父分类）**OR** 账户名（转出+转入）**OR** 金额 | `repo.dart:740-796` |
| 金额参与条件 | 关键词整体匹配 `^\d+(\.\d{1,2})?$` **且** 数字位 ≥ 2；小数点去掉后 `CAST(amount_cents AS TEXT) LIKE %digits%` | `repo.dart:783-793` |
| 为什么 ≥2 位 | 「5」几乎能匹配全部记录，噪音会盖掉真正命中的那几条 | 同上注释 |
| 转义 ② | 所有 `LIKE` 带 `ESCAPE '\'`；关键词按 `\` → `%` → `_` 顺序转义（反斜杠必须先转，否则二次转义） | `repo.dart:785-836` |
| 上限 | 500 条，多取一条判截断（标题带 `+`） | `repo.dart:863-886` |

文档出处：CH 1.4.4「搜索扩到…」、CH 1.4.5「修复」第 2 条、交接 §11「已知未修」（① 的 `%_` 未转义）。
**重建陷阱**：搜金额时把「38.5」按 38.5 元精确匹配（用户记不清具体金额，要的是包含关系）；不转义 `%`（搜「50%」命中全部）。

### 3.14 借贷的剩余 / 已还与「不许逾期负数」

| 规则 | 内容 | 依据 |
| --- | --- | --- |
| 已还不落库 | 每次查 `debt` 时按流水汇总：`repaid_cents = SUM(amount_cents) WHERE debt_id = d.id AND type = (借出→income / 借入→expense)` | `repo.dart:525-541` |
| 剩余 | `isClosed ? 0 : (amount - repaid).clamp(0, amount)` —— 多还的部分**不显示成负数** | `models.dart:1008-1012` |

| 逾期 | `closed_at == null && due_date 有值 && today > due_date` → 返回天数；否则 null | `models.dart:1014-1028` |
| 排序 | 未结清优先 → 有应还日的在前 → 应还日升序 → id 降序 | `repo.dart:536-539` |

### 3.15 交叉归集（负数怎么算）

| 规则 | 内容 | 依据 |
| --- | --- | --- |
| 口径 | 支出里的**负数**算进收入；收入里的**负数**算进支出；转账两侧都不参与 | `repo.dart:717-736`、`models.dart:506-526` |
| 语义 | 「这笔钱的方向反了，不是这一侧变少了」：代购代付后对方多给 20，记成支出 −20，统计上应体现为收入 +20 | `models.dart:506-511` |
| 谁必须一致 | 月度合计、筛选合计、饼图/排行、每日趋势、预算已用、内存侧 `sumBySide` —— 六处同一口径，否则「分项之和 ≠ 合计」 | `range_test`（分类饼图分项和==合计）、`side_total_test`（4 条）、`filter_test`（sumFiltered 与 sumBySide 同口径） |
| 饼图取绝对值 | 分类聚合对负数取绝对值 | `repo.dart:1142-1143` |

**重建陷阱**：饼图用 `SUM(amount)` 不取绝对值 → 有退款/净额负数的分类变成负扇区或消失；`sumBySide` 与 SQL 各写一套 → 日卡小计与月度合计对不上（这正是 `side_total_test` 存在的理由）。

### 4.2 迁移史

`Db._version` 演进（`db.dart:24-33`，② 到 57）。每一步都遵守同一条纪律：**只加列/加表，不动任何一行老交易**；迁移幂等（缺表跳过、列已存在跳过），因为「升级阶段抛异常 = App 直接打不开」。

| 版本 | 做了什么 | 实现要点 | 代码 |
| --- | --- | --- | --- |
| v2 | `txn_template` 加 `use_count` / `last_used_at` | 纯 `ALTER TABLE ADD COLUMN` | `db.dart:59-66` |
| v3 | 收入分类补「提成」 | 按「账本+类型+名称」查重；锚点「奖金」插其后；`sort_order` 位移必须限定 `type='income'`（支出/收入编号各自从 0 开始，有重复值）；缺 `ledger` 表就跳过 | `db.dart:67-70,436-503` |
| v4 | `txn` 加 `period_start` + 索引 | **只加列不改查询**；回填不在迁移里做（算期要读 `cycle_start_day` 与分类白名单），交给 `Repo.backfillMissingPeriods()` 在 boot 里跑 | `db.dart:71-73,505-529` |
| **v5** | `budget` 由自然月改为归属期 | SQLite 不能改约束 → **重建表**：建 `budget_v5` → `INSERT ... SELECT id, ledger_id, month\|\|'-01', category_id, amount_cents` → `DROP` → `RENAME`。账单日默认 1 时无损一对一（钱不变、条数不变） | `db.dart:74-76,531-563` |

| **v7** | 新建 `debt` + `txn.debt_id` | DDL 抽成 `_createDebtTable`（新建库与升级共用一份）；升级时若没有 `txn` 表就跳过加列（单测里的极简库）；补 `idx_txn_debt`。老数据 `debt_id` 全 NULL → 行为与升级前完全一致 | `db.dart:81-83,282-334` |

**迁移链上的两个特例**
1. **从备份恢复**不经过 `onUpgrade`（备份是直接往已建好的新表里灌行）→ 单独走 `Db.upgradeRestoredData()`（只做分类升两级，幂等）。
2. **恢复后回填**：`replaceTables` 末尾统一跑 `backfillMissingPeriods()`（旧备份没 `period_start`），② 再跑 `adoptCurrentBalances()`。

### 4.3 新软件必须「迁出」的字段（用户明确要能导入旧数据）

原则：**新软件的导入器应该直接吃旧版的 JSON 备份**（有 `schemaVersion` 与 `formatVersion`，是最可靠的迁移载体）；Excel 只能搬 `txn` 一张表，预算/目标/模板/周期/往来/账户余额全都不在里面（`backup_service.dart:27-29`）。

| 表 | 必须迁出的字段 | 说明 |
| --- | --- | --- |
| `ledger` | `id, name, icon, sort_order, archived` | `id` 必须保留（其他表的 `ledger_id` 指着它） |
| `account` | `id, name, kind, balance_cents, **opening_cents(②)**, include_in_total, sort_order, archived` | 缺 `opening_cents` 时用 §3.4 的「认基准」公式反算 |
| `category` | `id, ledger_id, type, name, icon, parent_id, sort_order, archived` | `parent_id` 是两级结构的全部；改名映射（`legacyNames`）只对 v5 备份需要 |
| `txn` | **全部 18 列**，尤其 `amount_cents`(可负)、`date`、`period_start`、`category_id`、`account_id`、`to_account_id`、`debt_id`、`recurring_id`、`template_id`、4 个详情列 | `period_start` 缺了 → 周期视图里这笔「消失」（② 体检会报「缺少归属期」）；`debt_id` 缺了 → 借贷流水被当成普通收支，月度支出虚高 |
| `budget` | `ledger_id, period_start, category_id, amount_cents` | 旧格式是 `month`（`2026-10`）→ `period_start = month + '-01'` |
| `debt` | `id, ledger_id, direction, counterparty, amount_cents, account_id, date, due_date, count_in_budget, closed_at, note` | **不要迁 `repaid_cents`**（派生值：按 `txn.debt_id` 重算） |
| `recurring` | 全部 12 列 | `next_run_date` 是补记的唯一起点 |
| `txn_template` | `id, ledger_id, name, icon, type, amount_cents, category_id, account_id, note, sort_order, use_count, last_used_at` | `use_count/last_used_at` 决定「最近 3 个」的顺序 |
| `saving_goal` | 全部 | 与流水不联动，直接搬 |
| `setting` | 只搬 `current_ledger_id`、`cycle_start_day`；**不搬** `app_name/schema_ready/ui.*` | 后者是「这台机器的状态」，搬过去会让新装的用户看到旧实验开关 |

**迁移验收标准**（建议新软件照抄）：恢复后 ①笔数、月度合计、账户余额与旧版逐项一致 ②每笔 `period_start` 非空 ③`data 体检` 干净（若新软件实现了对账） ④借贷「已还/剩余」与旧版一致 ⑤最近 3 个模板顺序一致。原项目的 `backup_test`（4 条）+ `migrate_v5_to_v8_test`（②2 条）就是这套验收的现成模板。

## 6. 重建取舍建议

> 前提：用户原话是「**只要功能能实现的效果一样就可以了**」。所以下面把「功能等价」和「实现等价」分开：**§3 的业务口径必须一字不差**，UI 框架、配色、图标、动画、状态管理都可以换。

### 6.1 必须一比一等价（口径错了就是另一个产品）

| 类别 | 条目 | 对应功能ID | 理由 |
| --- | --- | --- | --- |
| 金额 | 全程整数分 + 表达式只在最后取整 + 负数净额 | M12-F03 | 差 1 分就是账不平；净额记账是用户真实用法（代购代付） |
| 归集 | `period_start` 派生、抬期 R1（仅工资/奖金/提成 + 早于同月账单日）、短月收拢、翻期不越今天 | M02-F04、M04-F07、M12-F07、§3.3 | 账单日 ≠ 1 时全站数字都依赖它；抬期写错会「两个月工资挤一期」 |
| 排除 | 借贷流水不计收支/预算/饼图/趋势（6 处收敛点） | M02-F07、§3.2、§3.5 | 漏一处就有一个数字错，且用户看不出来 |
| 预算 | 可用额度 = 额度 + 本期计入预算的借入；已用=交叉归集支出；进度/剩余/每天可花全走可用额度；不结转 | M04-F02~F05、§3.1 | 「进度条 56% 但剩余对不上」是原项目专门修过的 bug |
| 余额 | `余额 = 期初 + 流水`（或等价的可对账结构）；净资产 = 账户 + 应收 − 应付 | M09-F01/F02、M10-F07、§3.4 | 这是 1.4.5 整版的主题：让「对不对」可判定 |
| 借贷 | 已还/剩余派生不落库；还款超额双层拦截；还满自动结清；借出恒不计预算 | M05、M12-F11、§3.14 | 剩余金额是这套功能最核心的数字 |
| 记账收口 | 保存后清筛选 → 游标对齐到这笔所在期 → 回明细 + 提示「已记账 · 区间」 | M12-F10、§3.6 | 1.4.1 的「记完看不见」会让用户重复记账（真实数据损失） |
| 周期补记 | 交易日期用应触发日；按 `recurring_id + date` 查重；按账本记「今天扫过」；三触发点 | M06-F04/F05、§3.10 | 唯一可能把房租记两遍的路径 |
| 筛选 | 筛选跨全部历史 + 列表有上限但合计不受限 + 明写范围 | M02-F11/F12、§3.7 | 两个数字并排不同口径 = 用户不再信任数字 |
| 备份 | 覆盖前必留快照、留不下就取消、一个事务、只跟 `current_ledger_id` 走 | M09-F09、M10、§3.12 | 单向操作没有退路是最容易失去用户信任的地方 |
