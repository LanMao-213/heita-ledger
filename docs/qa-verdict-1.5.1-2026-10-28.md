## 5. 金额显示新逻辑的边界 — PASS（穷举实测，无一处不一致）

### 5.1 被验收的实现

`lib/widgets/record_sheet/rows.dart:266-290` 的 `amountDraftText()`，两条路径：

- **纯字面量**（没按过运算符，`:278`）→ 回显用户敲的原文，只做「前导零剥离 + 整数位千分位」；
- **含运算符**（`:289`）→ 走 `_centsDraft()`，按分格式化并去掉无意义零。

关键约束：`lib/data/calc.dart:16` `_maxDecimals = 2`，`:38` 处按键第 3 位小数直接 `return expr`（拒绝）。

### 5.2 逐项核对表（**实测值**，非推演）

用临时探针（跑完即删）直接调 `amountDraftText()` 与 `Calc.cents()` 取值：

| 输入 | 显示值（实测） | 入库分值 | 可入库 | 判定 |
|---|---|---|---|---|
| `4` | `4` | 400 | 是 | 一致 |
| `4.` | `4.` | null | 否（确认键置灰） | 一致：保留小数点，表达"还没输完"，不回退成 0 |
| `4.3` | `4.3` | 430 | 是 | **一致（本次核心诉求：不再变 4.30）** |
| `4.30` | `4.30` | 430 | 是 | 一致：用户敲了两位就留两位，不替他截 |
| `1234.5` | `1,234.5` | 123450 | 是 | 一致（整数位加千分位，小数位原样） |
| `007` | `7` | 700 | 是 \* | 一致：前导零剥离，7 = 700 分 |
| `0.5` | `0.5` | 50 | 是 | 一致：`0.5` 的 0 保住（`^0+(?=\d)` 不吞孤零） |
| `12+` | `12` | null | 否 | 一致：末尾运算符剥掉后显示左操作数，不回退成 0 |
| `4.3+2` | `6.3` | 630 | 是 | 一致：结果路径去无意义零，不是 `6.30` |
| `-0.5` | `-0.5` | -50 | 是 | 一致：行首负号是净额语义，符号不丢 |

\* `007` 经键盘**不可达**（`calc.dart:45` 对 `cur=='0'` 做替换，按第二个 0 时得 `0` 而非 `00`），
属纯防御路径。显示 `7` 与入库 700 分仍然一致。

### 5.3 「显示值会不会和入库分值对不上」——穷举证明

不靠肉眼推，直接对**可达输入空间**做属性检查（BFS 应用 `Calc.press` 六层，
键集 `0 1 2 5 9 . + - * / del C`）：

```
PROBE| 可达表达式 203607 个，已比对 203607 个，其中可存 116913 个，不一致 0 个
PROBE| 数字键可达字面量 125000 个，三位及以上小数的 0 个
```

**结论：纯字面量路径下，显示值与入库分值不存在对不上的空间。** 原因是结构性的：

1. `_maxDecimals = 2` 保证字面量小数位 **≤ 2**（125,000 条字面量实测 0 例越界）；
2. 显示是**原文回显**（只动前导零和千分位，不动数值）；
3. 入库是 `round(值 × 100)`，对 ≤2 位小数**恒等**（无四舍五入分歧）。

两条路径共同封死了缺口，不是靠"碰巧没写到"。

### 5.4 唯一残余风险（P2，不阻断）

这个保证**挂在 `_maxDecimals = 2` 这一个常量上**，而 `amountDraftText()` 的字面量分支
对小数位数没有任何自己的护栏。若将来有人把 `_maxDecimals` 放开到 3：

- `4.305` 会显示成 `4.305`，而 `Calc.cents()` 存 `431` 分 → **显示 4.305 实际存 4.31**；
- `-0.004` 会显示成 `-0.004`，而 `cents = round(-0.4) = 0` → **显示负数实际存 0**。

当前不可达（已实测），但属于"一改常量就破"的隐性耦合。建议在字面量分支加一条
`frac.length <= 2` 的断言或改为按 `d.cents` 反推，把耦合显式化。

### P1（严重，不阻断 1.5.1，建议 1.5.2 修）

**P1-2｜老用户升级后界面「无声变脸」：深色 → 浅色，用户没做任何操作**

> 这条是我在 amend 带出的 `docs/decisions/OPEN-DECISIONS.md` 里发现、并回头查代码确认的。
> 它在团队自己的登记册里编号 **OD-01，状态 OPEN**（等产品拍板）。我把它记成 P1 而不是
> 让它留在"未决"里，是因为它影响**每一个存量用户**，而不只是某条次要路径。

- 代码事实（已有测试固化，非推测）：`Store.boot()` 读不到 `ui.theme` 键就回落
  `kDefaultTheme`；1.5.1 把 `kDefaultTheme` 从 `tower`（深色）改成 `holy`（浅色）。
  `test/theme_setting_test.dart:45` 的用例名就写着「老库没有 `ui.theme` → 出厂默认圣地 · 审判白」，
  且断言 `ThemeCtrl.i.dark == false` —— **该行为是被测试明确固化的，不是意外**。
- 影响面：所有**从未主动换过肤**的存量用户（默认值用户，通常是多数），升级 1.5.1 后
  第一次打开会觉得「界面被改了/设置被人动了」。账目、数据不受任何影响。
- 归因：默认值变更的**迁移路径没有处理**，且缺一个可靠的「升级 vs 全新安装」判据
  （无 install marker，历史库也没有）。团队已把判据问题写进 OD-01 的「卡在谁/什么」。
- 为什么我判 P1 不判 P0：不改任何数据、不影响任何功能可用性、用户可自行换回永夜；
  且这是**产品决策缺口**（该不该钉住老用户原皮肤），不是实现写错的缺陷。
- 若产品决定"钉住旧皮肤"：首次 boot 检测到「库已存在但无 `ui.theme`」时写一次 `tower`。
  难点在判据，不在代码量。
