## 2. 现在用户能做什么

### 导入账单（四步）
1. 「我的 → 从支付宝 / 微信账单导入」
2. 选 CSV → 逐行过目（**每行可独立勾选算入**，收入行默认不勾）
3. 选一个账户（顶部下拉）
4. 点「算入 N 条」

结束时报告**三个数字**，必须加得起来：算入 N / 你没勾 M / 账单内跳过 K。

**关键口径**：导入**不改余额**。因为这是历史账，钱早就花出去了。实现上是按账户把期初反向调一次，保持「余额 = 期初 + 流水」恒等式成立。

### 多选与批量
- 入口两个：顶栏最右「多选」图标；或**长按任意一行 → 菜单「多选」**
- 全选 / 全不选（只选**当前可见**的行）
- 批量改分类（支出/收入/转账混合会被拦下，理由见第 6 节）
- 批量删除（一个事务里完成，余额逐笔回滚）

### 按筛选导出
「我的 → 导出当前筛选结果」。筛选条件为空时会拦下并提示，避免用户以为导了筛选结果、实际是整本。

- 无第三方运行时依赖，`sqflite` 之外都是官方包

### 跑测试 —— ⚠️ 必须剥代理

本机代理会拦 `flutter_tester` 的本地 WebSocket，不剥的话测试直接挂：

```bash
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy \
    NO_PROXY=localhost,127.0.0.1 flutter test
```

应看到 `+459: All tests passed!`

单独跑某个模块把 `flutter test` 换成 `flutter test test/bill_csv_test.dart`。

### 静态检查
```bash
flutter analyze        # 应输出 No issues found!
```

### 打包
```bash
# 调试包（真机验证用，签名是 debug，别长期用）
flutter build apk --debug

# 正式包（需要 android/key.properties + release.jks）
flutter build apk --release --target-platform android-arm64
```

**这条命令以前是「名义上只出 arm64」。** `--target-platform` 只约束 `libapp.so`，
插件自带的 `.so`（这里是 dartjni）仍会按全 ABI 打进来，于是包里躺着
`lib/armeabi-v7a/` 与 `lib/x86_64/` 两个目录 —— 32 位设备装得上、一启动就闪退。

已在 `android/app/build.gradle.kts` 加 `packaging.jniLibs.excludes` 排除非 arm64，
现在 32 位设备在**安装阶段**就被 `INSTALL_FAILED_NO_MATCHING_ABIS` 拒绝。

**别用 `--split-per-abi` 发版**：它给 versionCode 加 `1000×ABI` 偏移（`23` → `2023`），
之后正常打包出来的版本号反而比它小，升级会卡死。这个坑是 2026-10-25 打包时被
`verify_apk.py` 的版本号校验抓到的。

### ⚠️ 打包目录不能带用户名

`libapp.so` 会嵌入构建期的绝对路径，实测形如
`file:///C:/Users/<用户名>/.../.dart_tool/flutter_build/dart_plugin_registrant.dart`。
Dart AOT 的行为，没有配置项能关。

**所以「在这台机器上直接 `flutter build apk`」打出来的包，等于把本机路径随包发出去。**
2026-10-25 之前的所有 APK 都带着它（第一批备份里 8 个包全中）。

发版要导出到中性路径再构建：

```bash
git archive HEAD | tar -x -C /c/hb/hl
cp android/key.properties /c/hb/hl/android/
cp android/app/release.jks /c/hb/hl/android/app/
cd /c/hb/hl && flutter pub get
flutter build apk --release --target-platform android-arm64
python <repo>/tools/privacy_scan.py --artifacts build/app/outputs/flutter-apk/app-release.apk
```

最后那条扫描必须输出「干净」。这一步不做，前面所有脱敏都白费。

### 出包校验（出包后必跑）
```bash
python tools/verify_apk.py <apk路径>
```

七项：包名 / 版本号 / `kAppVersion` / 签名 / 权限 / 图标 / ABI。全部 ✅ 才算能发。

自测脚本本身是否有效：拿一个别的 App 的包去跑，应当 FAIL 三项（包名、版本、debug 签名）。

### 隐私扫描（改文档、打交付物之后必跑）

```bash
python tools/privacy_scan.py --selftest         # 0. 先证明它还会红
python tools/privacy_scan.py                    # 1. 工作树
python tools/privacy_scan.py --history          # 2. 历史（最常被漏的一条）
python tools/privacy_scan.py --history \
    --artifacts ../xxx.bundle ../yyy.apk        # 3. 交付物（bundle 会解包后连历史一起扫）
```

**为什么要四条，而不是一条。** 2026-10-25 的泄漏恰好发生在"只跑第 1 条"上：
工作树改干净了、`git grep` 返回 0，看起来完成；但历史里 3 个提交仍带着
`C:\Users\<用户名>\...`，而推上公开仓库、交到别人手里暴露的正是历史。

`--selftest` 放在第一步是刻意的：这个脚本 10-24 建好之后**一直是红的**
（说明文档里为讲规则贴的示例「私钥头」被自己的规则命中），
没人发现，因为它没接进任何自动流程。永远红的工具会被忽略，永远绿的会被
信任——后者才是真正危险的。

## 6. 今天几个关键决策（为什么这么做）

| 决策 | 理由 |
|---|---|
| **导入不改余额**，改成按账户调期初 | 流水变了但余额不许变，这个差额只能由期初吸收。先减后补那种写法，任何一步漏了就是只能靠体检发现的漂移 |
| **GBK 不硬解**，明确报错 | Dart 没有内置 GBK 编解码，容错解出来是「锟斤拷」。**乱码一旦写进账本就几乎挑不出来**——宁可失败，失败可恢复 |
| **xlsx/PDF 在解码之前拦** | 这两种文件头都是 ASCII，UTF-8 解码**不会失败**。放在「解码失败后嗅探」里永远查不到（这是实测踩出来的） |
| **长按做菜单**，不是直接进多选 | `deleteTxn` 的 UI 入口只有长按这一处（编辑页没有删除按钮）。直接替换会把「删一笔」从 2 步变 3 步 |
| **混合类型禁止批量改分类** | 一个 `category_id` 不可能既是支出又是收入分类。强行归类会把另一侧挂到语义相反的分类下，预算和图表都会算歪 |
| **批量删除不循环调 `deleteTxn`** | 那样每条开一次事务，中途失败会留下「删了一半」——用户看到「已删除 20 笔」其实只有 8 笔没了 |
| **统计段单独成文件** | 这段口径最容易被改动，混在 2000 行里改一次得翻很久。拆完改口径只需看 2 个文件 |

## 7. 代码地图（新人先看这五个）

| 文件 | 看它干什么 |
|---|---|
| `lib/data/command.dart` | **写入门关**。所有写库走 `WriteGateway`，带事务与余额自检。**任何绕过它的写操作都是 bug** |

**一条铁律**：余额的唯一定义是 `余额 = 期初 + 流水合计`。凡是能让这两个对不上的改动，一律停手重想。
