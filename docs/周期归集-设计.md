# 周期归集 · 设计文档（F5）

> 状态：**阶段 0–2 已落地**（阶段 3 起待做）｜目标版本 1.1.2
> 前置决策：D12 自选周期起始日（= 账单日）、D13=C（预算仍按自然月）、D14 短月取月末
> **D22 工资抬期**：工资到账日与账单日不重合时，工资算进「下一期」；记录本身的日期不改，仍存真实发薪日

## 1. 要解决什么

现在所有统计口径都是自然月：明细列表、月份切换、月合计、分类饼图、每日趋势、筛选的「本月」。但很多人的钱是按「这张卡刷到什么时候」转的——账单日 15 号，工资 10 号到账，1 号到 30 号的月度汇总会把一笔工资和它要支撑的那半个月劈到两个格子里。

**目标**：让用户自己指定「每月从哪一天开始算一期」，明细与统计按这一期归集。

**两个独立的日子，不要混**：

| 日子 | 作用 | 谁决定 |
|---|---|---|
| **账单日**（周期起始日） | 切分明细与统计的格子 | 用户设置，1–31，默认 1 |
| **发薪日** | **只是一笔记录的真实日期**，不参与任何切分 | 银行决定，App 不关心 |

发薪日不落在账单日上时，靠「工资抬期」规则把工资挪到它支撑的那一期（见 2.3）。

**非目标**：不动预算口径（D13=C），不做多套周期并存，不强制每个账本一套周期。

## 2. 核心概念

| 概念 | 定义 | 谁在用 |
|---|---|---|
| 自然月（month） | `YYYY-MM`，1 号到月末 | 预算（`budget.month`） |
| 周期（cycle） | `[本月账单日, 下月账单日)`，含头含尾 | 明细、统计、筛选 |
| **归属期**（period） | 一条记录**算在哪一期**，与它的真实日期解耦 | 明细分组、合计、饼图、趋势 |

- **账单日**：用户自选 1–31（`cycle_start_day`），默认 **1**。
- **默认 1 等于自然月** —— 老用户升级后行为完全不变，只有主动改过才生效。这是本设计最重要的一条：**零感知迁移**。
- 区间用两个 `YYYY-MM-DD` 字符串表示（库里 `date` 就是字符串，字典序即时间序，直接 `BETWEEN`）。

### 区间怎么算

给定「今天」`d` 与起始日 `s`：

```
本月起始 = clamp(s, 当月天数)      # 29/30/31 遇到短月取月末（D14）
若 d.day >= 本月起始 → from = 本月起始, to = 下月起始 - 1 天
否则               → from = 上月起始, to = 本月起始 - 1 天
```

例：起始日 15，今天 10-17 → 本期 `10-15 ~ 11-14`；今天若是 10-10 → 本期 `09-15 ~ 10-14`。

**边界归属**：账单日当天算**新一期**（`>=` 而不是 `>`），前一天算上一期。这条要写进测试。

### 2.3 工资抬期（D22）

**要解决的问题**：账单日 15 号、工资 10 号到账。按 2.2 的算法，10/10 的工资落在 `09-15 ~ 10-14` 那一期，而它真正支撑的是 `10-15 ~ 11-14` 这一个月。用户看到的是「这期收入 1 万 2，却只花了两千」。

**规则 R1（一条 if，不需要发薪日设置）**：

```
若 这笔是工资类收入 且 date < 该自然月的账单日：
     归属期 = 该自然月账单日所在的那一期
否则 归属期 = date 所在的那一期
```

逐个场景验一遍（账单日 = 15）：

| 记录 | date | 落在哪期 | 抬期后 | 对不对 |
|---|---|---|---|---|
| 工资 | 10-10 | 09-15~10-14 | **10-15~11-14** | ✅ 正是要的效果 |
| 工资 | 10-14 | 09-15~10-14 | **10-15~11-14** | ✅ 账单日前一天也算下期 |
| 工资 | 10-17 | 10-15~11-14 | 不动 | ✅ 已在期内，不该再往后推 |
| 工资 | 09-20 | 09-15~10-14 | 不动 | ✅ 不会「抬两期」把两个月工资挤进一期 |
| 任意支出 | 10-10 | 09-15~10-14 | 不动 | ✅ 只对工资生效 |
| 工资，账单日=1 | 10-10 | 10-01~10-31 | 不动 | ✅ `10-10 < 10-01` 不成立，永不抬期 |

**为什么不用「发薪日」这个设置**：R1 只比较「date」和「同月账单日」两个已经存在的东西，不需要额外知道发薪日是几号。用户哪天发工资都行，早发晚发只要在账单日之前，就归下一期；晚于账单日，就归本期。少一个设置项，也少一处「设置值和实际不符」的隐患。

**副作用（要知道）**：账单日在发薪日之前（账单日 5、发薪日 10）时 R1 永不抬期——这正是对的，工资到了才开始新一期，本来就是本期的钱。

**如何识别「工资类收入」**：按分类白名单，见 2.5。

### 2.5 哪些收入进「抬期池」（D23）

判断标准只有一句：**这笔钱是不是「要用来支撑下一期生活」的主要收入。**

| 收入分类 | 进池 | 理由 |
|---|---|---|
| 工资 | ✅ | 已定 |
| 奖金 | ✅ | 已定；通常随工资一起发 |
| 提成 | ✅ | 已定；同上 |
| 兼职 | ❌ | 时间与金额都不固定。零星接单按真实日期更准，抬期反而失真 |
| 理财 | ❌ | 利息按日产生，抬期会把它和产生它的那段时间拆开 |
| 红包 | ❌ | 小额、当期性质 |
| 其他 | ❌ | 兜底，不确定的按真实日期 |

**为什么不做金额门槛**（比如「5000 以上才抬」）：同一个分类下金额差异很大，用户也没法预判哪笔会被抬，反而更难理解。分类边界是人自己能说清的，金额阈值不是。

**「提成」分类原本不存在 → 已按方案 A 落地**（D23，本次唯一动过的代码）：

原先的种子收入分类只有 6 个：工资 / 奖金 / 兼职 / 理财 / 红包 / 其他，没有「提成」。处理方式是补一个：

| 动作 | 实现 |
|---|---|
| 新装用户 | 种子收入分类加 `('提成', 'bonus')`，位置在「奖金」后面 |
| 老用户升级 | `_version` 2 → 3，`onUpgrade` 里调 `_addMissingIncomeCategories` |
| 查重 | 按「账本 + 类型 + 名称」查，用户早就自建过同名的就不插 |
| 排序 | 锚点优先级：紧跟「奖金」→ 插在「其他」前 → 排末尾。`UPDATE` 必须限定 `type = 'income'`（两个类型的 `sort_order` 各自从 0 开始，同账本内有重复值） |
| 容错 | 迁移链是多版本叠加的，缺表就跳过。**升级抛异常会让 App 启动阶段直接打不开**，比少一个分类严重得多 |
| 断言 | `test/upgrade_test.dart` 三条：全新安装顺序、老库升级补插、「已有自建同名声」不重复 |
| 真机验证 | 已在一台装过 v2 老库的华为 LNA-AL00 上覆盖安装：分类管理显示「支出 10 · 收入 7」，收入顺序为 工资 → 奖金 → **提成** → 兼职 → 理财 → 红包 → 其他，旧账目（1 笔 2.00）完好 |

**白名单要可配置，但不用现在做**：先按上表硬编码，用户自建分类默认不进池；等有人真的需要，再在设置页开一个勾选列表。现在做多选框，收益是 0，成本是一屏 UI。

**白名单判断不能只看分类**——分类可以被改名、被删、自建。所以它只决定**默认值**，每笔仍然可改（见 5.2）。这条是整个 D22 设计里唯一强依赖用户意图的地方，必须留手动口。


### 2.4 归属期与真实日期并存

这是整套设计的支点，写清楚免得后面有人改错：

| 场景 | 用哪个日期 |
|---|---|
| 明细列表按天分组、组内排序 | **真实 date** |
| 明细列表分到哪一期 | **归属期** |
| 合计 / 饼图 / 趋势 / 概览卡 | **归属期** |
| 筛选面板的「时间」区间 | **真实 date**（用户筛「10月1日–31日」必须能筛到 10/10 的工资） |
| Excel 导出、搜索结果的日期列 | **真实 date** |
| 预算（D13=C） | **真实 date 所在自然月** |

后果：明细页某一期的分组里，可能有一笔日期比该期起始日更早的记录（10 期的组里躺着 10-10 的工资）。这是**故意的**，列表项显示真实日期，用户看到「10 月 10 日」就知道那是发薪日，不会误认为数据错乱。

**抬期不影响的东西**（这点要跟用户说清，否则会误以为在改账）：

| 不受影响 | 说明 |
|---|---|
| 账户余额 | 钱 10 号到账，账户余额 10 号就增加，与 `period_start` 无关 |
| 记录的日期 | `date` 一个字不改，列表、导出、搜索看到的还是 10 号 |
| 筛选的时间区间 | 按真实日期筛，筛「10 月」能筛到 10 号那笔 |
| 支出归属 | 支出永远按真实日期归期，不抬 |

**一个退路**：如果用户发现「工资到账后那几天的花销，总感觉算在上一期」，那不是 bug，而是账单日选得离发薪日太远。**把账单日直接改成发薪日**，抬期规则就永久不触发（`date < 账单日` 不成立），一期正好从发工资那天开始。D22 这套设计是「账单日不重合时也能凑合」，不是「必须不重合」。


## 3. 数据层

### 3.1 存储

**设置项**（不动表）：

| key | 值 | 默认 |
|---|---|---|
| `cycle_start_day` | `"1"`–`"31"` | `"1"` |

**表结构：`txn` 加一列**（这是相对旧版设计的唯一实质变化，由 D22 引起）：

```sql
ALTER TABLE txn ADD COLUMN period_start TEXT;                 -- 归属期第一天，YYYY-MM-DD
CREATE INDEX idx_txn_ledger_period ON txn (ledger_id, period_start);
```

- `date` **一个字都不改**——它永远是真实发生日（用户要求「存储按发薪日来算」）。
- `period_start` 是**派生字段**，随时可以从 `date + cycle_start_day + 是否工资` 重算出来，所以它不是新的事实来源，只是把它物化下来让查询能走索引。
- 为什么物化而不是每次现算：现算要在 SQL 里写 `CASE WHEN strftime('%d', date) < 15 ...`，四个查询各写一遍，索引全废，且规则改一次要改四处。物化一次，查询只比区间，规则只在一处。

**迁移与回填**：`db.dart` 的 `_version` **3 → 4**（3 是补「提成」分类用掉的），`onUpgrade` 里加这段（与已有的 `if (oldVersion < 2)` / `< 3` 并列）：

```dart
if (oldVersion < 4) {
  await db.execute('ALTER TABLE txn ADD COLUMN period_start TEXT');
  await db.execute('CREATE INDEX idx_txn_ledger_period ON txn (ledger_id, period_start)');
}
```

回填**不在迁移里做**，放在 `boot()` 之后的一次性任务里（读当前 `cycle_start_day` 才能算）：

```dart
// period_start 为空的记录统一补一遍；起始日默认 1 时结果等于月初，行为不变
await Repo.rebuildPeriods(ledgerId);
```

**改账单日 / 改抬期规则时必须重算**：

```dart
static Future<void> rebuildPeriods(int ledgerId) async {
  // 一条 UPDATE 用 SQL 算，不要 for 循环逐条 update
  // 只更新真正变化的行，避免几千条无意义写入
}
```

几千条记录毫秒级（`perf_probe` 实测同量级全表扫 1.4ms），不需要进度条，但要包在事务里。

### 3.2 纯函数（新增 `lib/data/cycle.dart`）

```dart
/// 某一期区间的起止日期（YYYY-MM-DD，含头含尾）
(String from, String to) cycleRange(DateTime d, int startDay);

/// 按「期」平移：shiftCycle(d, +1) 拿下一期的起点
DateTime shiftCycle(DateTime d, int startDay, int delta);

/// 把某个月的起始日按当月天数收拢（29/30/31 → 月末）
DateTime cycleStartOf(int year, int month, int startDay);

/// ★ 归属期：这笔算在哪一期。R1 抬期规则只在这里实现一次。
String periodOf({
  required String date,        // 真实发生日
  required int startDay,       // 账单日
  required bool liftToNext,    // 是否工资类收入（由调用方按分类判定）
});
```

单独成文件、纯函数，可以脱离 UI 和数据库单测——这是整件事里最容易算错的部分，尤其是 `periodOf`。

### 3.3 Repo 改造

现状按月查询的方法有四个，统一改成收区间，且**区间条件打在 `period_start` 上，不是 `date`**：

| 现有签名 | 改成 | 过滤字段 |
|---|---|---|
| `monthTotals(ledgerId, month)` | `rangeTotals(ledgerId, from, to)` | `period_start` |
| `categoryStats(..., month, ...)` | `categoryStats(..., from, to, ...)` | `period_start` |
| `dailyTotals(ledgerId, month)` | `rangeDailyTotals(ledgerId, from, to)` | `period_start`，但**分组仍按 `date`**（趋势图的柱子是真实日期） |
| `listTxns(..., month: ...)` | `listTxns(..., from:, to:)` | `period_start`，排序仍 `date DESC` |

`searchTxns` **不改**——搜索是跨期的，按 `date` 筛，与周期无关。

**过渡策略（重要）**：不要一次性改所有调用点。先新增 `range*` 版本，让旧的 `month*` 方法内部委托给新方法（把月折算成月初/月末）。这样：

1. 数据层先落地、可测，UI 完全不动，随时可合并；
2. 之后逐个调用点切到 `range*`，每切一个跑一次回归；
3. 全部切完再删旧方法，删除前用 `grep` 确认零引用。

`monthStart/monthEnd` 两个辅助函数保留，`monthTotals` 委托时还要用。

**写入路径**：`insertTxn` / `updateTxn` 都要写 `period_start`。规则集中在 `periodOf`，写入前算一次。改一笔的日期或分类时同步重算——这是最容易漏的地方，测试要盖住。

## 4. 状态层

`Store` 现在只有一个 `month` 字段，被三件事共用：明细、统计、预算。周期化之后要拆开：

| 字段 | 含义 | 用途 |
|---|---|---|
| `cycleFrom` / `cycleTo` | 当前期的起止日期 | 明细、统计、筛选默认区间 |
| `month`（保留） | 当前自然月 `YYYY-MM` | **只给预算用** |

- `loadMonth()` 拆成 `loadCycle()`（明细/合计/统计/趋势）+ `loadBudget()`（预算相关）。
- `shiftMonth(delta)` 改成 `shiftCycle(delta)`：按起始日平移一期。
- `monthIsCurrent` 改成 `cycleIsCurrent`（当前期是否包含今天）。
- 切账本/清库的重置逻辑不变。

### 5.2 「临时算进下一期」——每笔的手动覆盖

R1 自动判定时，用户看不到发生了什么。三种处理：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 收入类型下、日期行右侧出现一行小字：「这笔算 10-15 起的这期」，可点切换。默认值按 2.5 的白名单（工资/奖金/提成→开，其余→关） | 一行 UI，面板目前有空间（R1 腾出的高度还在） |
| B | 完全隐式，不加任何提示 | 用户会问「为什么这笔工资在下一期」 |
| C | 只做隐式，但在明细列表那笔记录上加「↑ 已计入下期」的弱标记 | 列表变复杂，且事后才看得到 |

选 A。

**「临时」的确切含义**（这是用户明确要的那个「临时补充进池子」）：

| 是 | 不是 |
|---|---|
| 只作用于**当前这一笔** | 不写进设置，不影响下一笔 |
| 记完就复位，下次开面板回到白名单默认值 | 不修改分类，不改「哪些分类算下一期」 |
| 一笔兼职收入想算下期，切一下就行 | 不需要先把它挪进「工资」分类 |
| 点回去就取消，随时可逆 | 不留下任何持久化痕迹 |

**所以设置页不需要「哪些分类算下一期」的勾选列表**——那个界面收益为 0：真要例外时，用户当场切开关比去设置里找更快，而且设置里改完还会影响以后所有记录，反而不如「临时」精确。

**状态存哪**：不新增表字段。`period_start` 已经把它表达出来了——写入时若 `period_start != date 所在期的起始日`，就是这把开关打开着。打开一笔旧记录时，开关状态直接反推，不需要额外的 flag。

**与 R1 的关系**：R1 算的是**默认值**，开关是**最终值**。写入顺序是「白名单给初值 → 用户可改 → 落库时以最终值算 period_start」，不存在两套规则打架。



### 5.3 明细列表的呈现

某期里出现「日期早于该期起始日」的记录时，列表项**照常显示真实日期**，不加特殊标记——加标记反而会让人以为数据异常。用户知道自己是 10 号发工资，看到「10月10日」出现在这一期里就是对的。

只有在**筛选结果**（跨期）时，分组头才需要显示归属期，否则一堆日期会乱。这个细节在阶段 3 处理。

## 6. 边界情况

| 情况 | 处理 |
|---|---|
| 起始日设 29/30/31，当月没有这天 | 取当月最后一天（D14）。2 月 → 28/29 号 |
| 12 月的期跨年 | `to` 落在次年 1 月，日期字符串天然支持 |
| 今天正好是起始日 | 新一期第 1 天（`>=` 判定） |
| 期长 28–31 天不等 | 趋势图按区间天数画，不能写死 31 |
| 明细为空 | 与现在一致，空状态文案不变 |
| 预算跨期 | 预算卡显示自然月，明确标注；不做跨期分摊（D13=C 的代价，可接受） |
| 工资在账单日**之后**到账（如 10-17 付、账单日 15） | **不抬期**，就归当前期。R1 的 `date < 账单日` 不成立，无需特判 |
| 一个月记了两笔工资（工资 + 年终奖） | 两笔都按 R1 各自判定；同在账单日前的都抬到同一期，符合直觉 |
| 用户把工资记在「其他」收入下 | R1 不生效（不是工资分类）。靠 5.2 的开关手动改，或改回工资分类 |
| 账单日从 15 改回 1 | 必须跑 `rebuildPeriods`，否则旧的 `period_start` 停在 15 号起点，明细会错位 |
| 改了某笔的日期/分类但没重算 `period_start` | 这笔会留在旧期。**这是最隐蔽的一个坑**，写入路径测试必须盖住 |

## 7. 测试计划

| 类型 | 覆盖 |
|---|---|
| 纯函数 `cycleRange` | 起始日 1/15/28/31；跨月、跨年、2 月、闰年；边界日归属（起始日当天进新期、前一天留旧期） |
| 纯函数 `periodOf` | 2.3 那张表的 6 个场景逐个断言；`liftToNext=false` 时永不抬期；账单日=1 时结果等于 `date` 月初 |
| 数据层 | `rangeTotals` 的区间含头含尾；区间外一天不进合计；负数交叉口径在新区间下仍然成立 |
| 归属期一致性 | 同一期的「列表条数」必须等于「合计里的 `cnt`」——这条能一次性抓住所有错位 |
| 写入路径 | 新增/改日期/改分类三种情况都要重算 `period_start` |
| 迁移 | `_version 3 → 4` 升上来后，老数据的 `period_start` 全部非空且等于月初（起始日默认 1）；v1/v2 直升级的路径也要能走到（迁移链不能断） |
| 回归 | 现有 45 条必须全绿；`ui_shot` 的月份断言要跟着改 |
| 端到端 | 起始日改 15 → 明细列表变成 10-15~11-14 → 记一笔 10 号工资 → 出现在 10-15 期 → 切上一期 → 筛选「本期」区间一致 |

| 阶段 | 内容 | 产出 | 工时 |

**版本号注意**：阶段 0 已经把 `_version` 推到 3（补提成分类）。阶段 2 加 `period_start` 时是 **3 → 4**，别照着旧文档写 2 → 3，那会让已升级过的设备再跑一遍 v3 迁移。

**阶段 2 的关键**：加列且回填后，先**不**改任何查询——此时 `period_start` 只是躺着，`date` 仍是唯一查询依据，行为 100% 不变。这一步可以单独发出去，等稳定了再切查询。这样「迁移」和「口径切换」是两次独立的风险。

**回滚**：每阶段独立提交。阶段 1–3 无行为变化，回滚零成本。阶段 4 之后要回滚，把 `cycle_start_day` 读回 1 并跑 `rebuildPeriods`，即恢复自然月行为，数据无损（`period_start` 多出来但不再使用）。

### 8.1 阶段 2 实现记要（2026-10-18）

| 项 | 实际做法 | 与设计的差异 / 原因 |
|---|---|---|
| 迁移 | `_addPeriodStartColumn()`：查 `sqlite_master` + `PRAGMA table_info`，缺表跳过、列已存在跳过、索引 `IF NOT EXISTS` | 比设计更保守。迁移链多版本叠加，升级抛异常会让 App 打不开 |
| 回填时机 | `Store.boot()` 里 `Repo.backfillMissingPeriods()`；恢复备份后由 `Repo.replaceTables()` 末尾再补一次 | 设计只写 boot 一处。恢复旧备份（v3）后同样会出现空值，多补一处才闭环 |
| 重算实现 | 「一次查询 + 一次 batch UPDATE」，只写有变化的行 | 设计写的是「一条 SQL UPDATE」。短月收拢（D14）+ 抬期白名单（D23）在 SQL 里要两层 CASE + julianday，还会跟 `periodStartOf` 各维护一份口径。几千行毫秒级，口径唯一更重要 |
| 写入路径 | `insertTxn` / `updateTxn` / `runDueRecurring` 三处全部走 `_txnRow()` + `periodFor()` | 设计只点名前两处。**周期账单自动补记也直写 `txn`**，漏了它那些记录会永远停在 NULL |
| 模型 | `Txn.periodStart` 只读；`toMap()` **不含**该字段 | 归属期是派生值，只能由 Repo 算。放进去等于给「调用方漏传」留了口子 |
| 测试 | `test/period_test.dart` 18 条 + 全量 117 条 | 覆盖 v3→v4 迁移、回填幂等、抬期 6 个场景、改日期/改分类重算、币种无关的跨年边界 |

**副作用（要知道）**：`record_keypad_test` 两条原先靠 `pumpAndSettle` 等写入的用例，因为写入路径多了几次数据库往返而查得太早，已改为让出一次真实事件循环再查库（不涉及产品行为）。

## 9. 风险


| 风险 | 影响 | 应对 |
|---|---|---|
| 双口径让用户困惑（明细按周期、预算按月） | 用户觉得「数字对不上」 | 预算卡标题标明「自然月」；周期条显示明确区间而不是「10月」 |
| 调用点遗漏（某个页面还在用旧 `month*`） | 局部统计口径不一致，很难发现 | 旧方法委托新方法 → 过渡期不会出错；最后用 grep 清点 |
| 趋势图写死 31 天 | 期长 28 天时右侧空一片或越界 | `_DailyTrend` 改按区间天数生成 |
| 截图与测试断言大面积变 | 回归成本 | 阶段 4 集中处理，不在前三个阶段动截图 |
| **`period_start` 与实际不一致**（漏重算） | 某笔记录凭空消失或重复出现，且用户无法自查 | 写入路径统一走一个 helper；加「列表条数 = 合计 cnt」的一致性断言 |
| **抬期规则被误解为 bug** | 用户看到「10 号的工资在 11 月那期」以为是错的 | 5.2 的开关让它在录入时可见；明细项显示真实日期 |
| **改账单日后忘记重算** | 全部历史错位，最严重 | 设置页改动后同步调 `rebuildPeriods`，且写完立刻读回比对条数 |
